# Модель угроз и статус защиты

[English](THREAT-MODEL.en.md) · Draft / Experimental · 01.11.2026

| Свойство | Механизм | Граница результата |
|---|---|---|
| Целостность | SHA-256 по доверенному эталону, digest в подписанной лицензии | Один SHA-256 не удостоверяет автора |
| Подлинность | Ed25519, заранее настроенный trust root | Подписанный вредоносный код остаётся вредоносным |
| Право исполнения | Подписанные execute, сроки, ключи установки; online grant | Не заменяет коммерческий договор, не считает камеры |
| Конфиденциальность архива | SealedBox для ключа установки | Plaintext нужен runtime, доступен доверенному администратору |
| Копирование только ciphertext | Привязка к ключу установки | Клон установки вместе с секретами не блокируется |
| Изоляция стороннего кода | Требование к host/supervisor/worker | В reference Python library не реализована |
| Обфускация/компиляция | Возможный дополнительный профиль | Не реализована и не требуется для базового обмена |
| Защита весов | Включение весов в envelope, свой license scope | Отдельно доставленная модель автоматически не защищена |

Прототип даёт существенно больше, чем открытый Python ZIP: копия поставки без ключа не раскрывает включённые код и данные, а изменение лицензии обнаруживается до исполнения. Он не предотвращает реверс-инжиниринг доверенным администратором. `.pyc`, обфускация и native extension могут повысить стоимость анализа, но не заменяют криптографию и управление лицензиями.

## Недоверенный пакет

На первом пилоте допускается только проверенный код издателя. Для расширения на недоверенных авторов нужна отдельная граница исполнения:

1. Supervisor проверяет источник, подпись, manifest, разрешённый профиль и заранее утверждённый набор зависимостей. Установка через pip, скрипты установки и скачивания во время открытия пакета запрещены.
2. Код запускается в отдельном worker на отдельного UID без root, Docker socket, host PID namespace, ключей издателя/лицензионного сервера и секретов других решений. Runtime image фиксируется digest и проходит dependency review.
3. Root filesystem read-only; входные данные/package read-only; временные данные на приватном tmpfs; нет монтирования домашнего каталога, произвольных путей host и устройств. Ограничить доступ к `/proc`, dumps и IPC соседних процессов.
4. Сеть worker по умолчанию отключена. Лицензирование выполняет доверенный supervisor; доступ к утверждённым model services — через узкий посредник с allowlist, квотами и таймаутом. Право worker генерировать события не означает право обращаться к бизнес API.
5. Ограничить CPU, RAM, PIDs, file size, объём входов/выходов, частоту событий и длительность вызова. Supervisor убивает зависший процесс и не принимает частичные результаты. Нужны seccomp и AppArmor/SELinux; контейнер не гарантирует защиту от всех атак ядра.
6. Вход/выход — строгий JSON/typed contract, без pickle и произвольных Python objects. Supervisor проверяет последовательность, state/event schemas, lease и идемпотентность до публикации события. Не принимать из worker флаг «лицензия проверена».

Разделение процессов ограничивает доступ к ключам платформы, но не скрывает plaintext самого сценария от сценария или администратора. Для сильной изоляции враждебных tenants следует оценить отдельные VM/microVM; это дальнейшая работа.

## Проверка принимающей системы перед production

Обязательные испытания: попытка записи вне tmpfs; попытка обращения в сеть и к host; исчерпание памяти, CPU, PIDs; зависание; избыточный output; вредоносная зависимость; некорректный JSON; ложное событие; истечение lease во время вызова; падение и восстановление worker. Эти испытания контейнерной границы в текущем пакете не проведены. Наличие Python unit tests не является их заменой.

Online-прототип проверяется на loopback. Production требует HTTPS, устойчивых replay/revocation stores, rotation, rate limits, мониторинга и аудита. Offline требует контроля ключей/часов и согласованной политики переноса. GPU/TPM/TEE, работа под атакой администратора и промышленная сертификация не проверены.

[Docker: seccomp](https://docs.docker.com/engine/security/seccomp/) описывает ограничения syscalls; это основание требований к Linux host, а не свидетельство выполненного теста.
