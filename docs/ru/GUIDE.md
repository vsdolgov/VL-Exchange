# Практическое руководство VL Exchange

**Draft / Experimental · [English](../en/GUIDE.md)**

Здесь показано, как подготовить пакет модели или сценария и подключить его к принимающей платформе. Примеры используют синтетические данные и запускаются локально.

## Экспорт модели

Сначала выберите поддерживаемый профиль. Для исходного VLMP 0.1 нужны `CustomModelProtocol` и его SDK. Публичный профиль 0.2.0-draft.1 — отдельное предложение, которому закрытый SDK не нужен. Эти профили нельзя подменять друг другом. Для начала используйте [синтетический пример](../../model/examples/channel-classifier) и его [спецификацию интерфейса](../../model/spec/SPECIFICATION.ru.md).

Чтобы подготовить пакет:

1. Реализуйте `Model.preprocess` и `Model.postprocess`, включите необходимые вспомогательные функции.
2. Опишите вход BGR `uint8` HWC, преобразование в RGB, изменение размера и нормализацию. Укажите имена и формы входов и выходов ONNX, названия классов и `category_id`.
3. Перечислите публичные зависимости, версию Python и необходимые возможности.
4. Добавьте не менее трёх разных входов `.npy` без pickle. Для каждого укажите ожидаемые класс, оценку, ID, индекс и допустимые отклонения.
5. В `files` перечислите все файлы, кроме манифеста, и их хеши SHA-256. Не добавляйте данные заказчиков без разрешения.

Чтобы пересобрать и проверить пример, выполните из корня репозитория:

```sh
python model/tools/build_demo.py
python model/src/public_model.py validate model/examples/channel-classifier
python model/src/public_model.py golden model/examples/channel-classifier
python model/tools/independent_host.py model/examples/channel-classifier
python tools/model_archive_roundtrip.py
```

Пересоберите пакет до фиксации версии. Оба исполнителя должны получить один и тот же пакет без изменений. Сохраните хеши манифеста, файлов и ZIP, а также версии окружения. Недостаточно сравнить только первый результат: нужно проверить и оценки.

`model_archive_roundtrip.py` проверяет безопасные пути в ZIP, отсутствие символьных ссылок и имён, различающихся только регистром, ограничения ресурсов и полный список файлов. Затем он отдельно распаковывает один и тот же архив во временный закрытый каталог для каждого исполнителя и запускает их в отдельных процессах. Все 13 результатов каждого исполнителя сравниваются с ожидаемыми результатами и друг с другом. До и после проверки сверяются хеши SHA-256 архива, манифеста и каждого файла; затем временные каталоги удаляются. Это проверка поставки архива локальным исполнителям, а не испытание платформы другого производителя.

## Экспорт сценария

Реализуйте `Scenario(**parameters)` и `process(inputs,context,state)`. Последний метод возвращает только `{events:[{event_type,payload}],state}`. Всё, что может повлиять на будущие события, храните в состоянии JSON. Код не обращается к внутреннему графу VL и не выполняет внешние бизнес-операции сам.

Опишите смысл каждого события, пороги, единицы измерения и правила работы со временем. Подготовьте схемы, значения по умолчанию, ограничения и тестовые последовательности с полными ожидаемыми событиями исполнителя.

```sh
python scenario/tools/build_demo.py
python -m vl_scenario_package validate scenario/examples/target-scenario --policy development --check-environment
python -m vl_scenario_package golden scenario/examples/target-scenario --policy development
python scenario/tools/independent_host.py scenario/reports/vlsp-target-scenario.zip
```

Последняя команда запускает один и тот же ZIP у независимого исполнителя в режимах development, offline и online. Только для проверки online используется временный локальный HTTP-сервер. Постоянные ключи не сохраняются. События, состояние, сброс и обработку ошибок определяет [спецификация VLSP](../../scenario/spec/SPECIFICATION.md).

## Адаптер принимающей платформы

Принимающей платформе нужен адаптер, который подготовит входные данные, запустит пакет и обработает результат:

1. Укажите точные формат, версию, профиль и возможности. Неизвестные обязательные элементы отклоняйте до загрузки кода. Отдельно проверьте список файлов, граф, зависимости и права.
2. Явно сопоставьте камеры или потоки с `source_id`, а логические сессии — с `run_id`. Назначайте строго возрастающий `sequence` и неубывающее время UTC Unix в `event_time_ms`. Исходный PTS преобразуйте явно.
3. Запустите модель и передайте её реальный результат как `{classification:{label,score,category_id,output_index}}`. Тестовый JSON не является результатом работы модели. VLSP 0.1 не задаёт скрытые вызовы модели. Публичный VLMP 0.2 подключается явным сопоставлением; исходные `model_links` остаются в версии 0.1.
4. Исполнитель хранит состояние JSON отдельно для каждого манифеста, экземпляра, источника и запуска. Он создаёт оболочки и идентификаторы событий и атомарно фиксирует события и состояние после всех проверок. Внешнюю доставку, outbox и устранение дублей обеспечивает интеграция.
5. Обеспечьте изоляцию процессов, права доступа к файловой системе и сети, а также ограничения ресурсов. Пространства имён при импорте и проверка времени после возврата вызова не заменяют изоляцию и принудительную остановку. Оба демонстрационных исполнителя запускают доверенный код Python.
6. При коммерческой поставке устанавливайте доверие к издателю независимо от содержимого пакета. Проверяйте автономное разрешение или онлайн-допуск до расшифровки и импорта, а то же временное разрешение (`lease`) — перед фиксацией результата. Администраторы считаются доверенными. Защищённый исполнитель модели для нового публичного профиля пока требует отдельной интеграции.

## Защищённый сквозной пример

```sh
python tools/test_pipeline.py
```

Команда запускает настоящую модель ONNX и передаёт результат классификации защищённому VLSP в режимах offline и online. Она создаёт временные ключи получателя, установки, издателя и сервера; после проверки оболочки и открытый текст удаляются. Протокол защищённой поставки описан [отдельно](../security/SPECIFICATION.ru.md). Это проверка доверенных прототипов, а не инструкция по промышленному управлению ключами.

## Роль ИИ при переносе

ИИ-помощники могут упростить написание адаптеров, разбор чужого API и перенос прикладной логики. Общий интерфейс помогает проверять результат этой работы и не тратить ресурсы на повторную интеграцию, сохраняя конкуренцию платформ и разработчиков. ИИ не заменяет согласование смысла событий и условий лицензии, а также испытание одного неизменённого пакета в независимых системах. Мы не обещаем конкретный процент экономии.

## Частые вопросы

**Обязательно пользоваться платформой или облаком VL?** Нет. Принимающая платформа реализует открытые интерфейсы и свой адаптер. Для автономной поставки облако не нужно.

**Зачем это при наличии ONNX, API и ONVIF?** Эти технологии решают разные части задачи. Для переноса прикладной логики платформам также нужно согласовать обработку данных, состояние, смысл событий и ожидаемые результаты проверок. VL Exchange дополняет существующие технологии.

**Нужно открыть исходники и веса?** Нет. Открыты интерфейсы; коммерческие права и защищённая поставка рассматриваются отдельно. Публичные примеры используют синтетические данные. Финальные лицензии проекта пока не утверждены.

**Оплаченная лицензия автоматически заработает на другой платформе?** Нет. Возможность переноса — целевой коммерческий принцип, если это допускают условия правообладателя. Сейчас поставка привязана к ключу получателя. Для переноса нужен согласованный перевыпуск, а отзыв при автономной работе происходит не мгновенно.

**Можно доверять любой подписанной модели?** Нет. Подпись подтверждает ключ, но не безопасность кода. Текущий исполнитель рассчитан на доверенных издателей и администраторов. Принимающая платформа должна изолировать недоверенный код.

**Что проверено сейчас?** Смотрите [матрицу совместимости](COMPATIBILITY.md). Два локальных исполнителя не подтверждают поддержку платформы другого производителя или GPU.
