# Первый межвендорный пилот

[English](PILOT.en.md) · План, не выполненное испытание

Цель — один неизменённый пакет, исполняемый VL и независимо реализованным host партнёра, с сопоставимыми результатами и сохранением согласованного коммерческого права заказчика. Участник, сроки и обязательства пока не согласованы. Прежние контакты не означают согласие на участие.

## Материалы партнёру

Передать одобренный tag Draft, обе спецификации и схемы, открытый синтетический ZIP, manifest/inventory/digest, golden inputs и expected outputs, negative vectors, quick start и минимальный host. Указать общий crypto/runtime stack и ограничения профиля. Для VLMP0.1 исходный SDK-профиль и новый public experimental профиль считать разными; не требовать доступ к закрытому SDK для public пути.

От партнёра нужны: объявленные Python/OS/CPU/runtime версии, адаптер входов/контекста и событий, отдельный host lifecycle, политика trust roots, безопасный worker и описание offline/online установки. Перенос собственного визуального редактора и внутренних блоков не нужен. Для проверки коммерческой защиты издатель выдаёт отдельные тестовые ключи и права без реальных секретов или клиентских данных.

## Последовательность и критерии

1. Согласовать конкретные profile/version, права на материалы, критерии сравнения и публикации. Для ONNX заранее задать atol/rtol; события, идентификаторы, ошибки порядка и state сравнивать по спецификации интерфейса.
2. Зафиксировать SHA-256 ZIP и всех файлов до передачи. Партнёр реализует host независимо от reference executor; зависимости/общие компоненты раскрыть.
3. Запустить один ZIP на обеих системах: VLMP golden inputs, повторы/порядок; VLSP вся последовательность, reset, Unicode ID, state и ошибки. После сравнить digest пакета.
4. Проверить offline и online: неверные ключи, подпись, tamper, expiry, replay, отзыв, отказ сервера, истечение во время вызова. Сценарий не должен публиковать внешние события до supervisor commit.
5. Провести отдельные испытания изоляции worker и ограничений ресурсов. Их результат не выводить из положительных unit tests.
6. Отработать migration на новую установку с перевыпуском envelope и сохранением исходного ZIP; подтвердить договорное право без повторной покупки аналитики. Для offline зафиксировать ограничение отзыва и согласованную деактивацию.
7. Успех: все обязательные vectors проходят без изменения ZIP; результаты в допусках; описаны отказы/ограничения, повторный запуск воспроизводим сторонним инженером.

Публикуемый протокол содержит даты, согласованные названия участников, profile/version, commit, среды, команды, hashes, таблицы результатов и известные ограничения. Публикация названия/логотипа партнёра — только после его согласия. Не публиковать адреса промышленных систем, ключи, журналы с персональными данными или коммерческие веса.

Ориентир после согласования: неделя 1 — спецификация интерфейса и адаптер, неделя 2 — совместные тесты, неделя 3 — migration/security и протокол. Это оценка ассистента, не обязательство сторон и не дата запуска.
