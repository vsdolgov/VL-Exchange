# VL Exchange — VL Model Package (VLMP) v0.1

> Историческая редакция интерфейса0.1.0, сохранённая для реализаторов. [English](SPECIFICATION.en.md). Этот профиль требует внешний `vlmodels-types1.8.1` и Torch; SDK и закрытый код здесь не распространяются. Публичный исполняемый профиль0.2.0-draft.1 — отдельное [предложение](../../../model/spec/SPECIFICATION.ru.md), не замена0.1.0. Текст ниже сохраняет требования исходного пилота; публикация прав на внешние зависимости этим документом не подтверждается.

**Версия интерфейса: 0.1.0. Статус: проект нормативной спецификации для проверяемого пилота.**

Ключевые слова MUST / ДОЛЖЕН, MUST NOT / НЕ ДОЛЖЕН и MAY / МОЖЕТ обозначают обязательное требование, запрет и допустимую возможность. Требование спецификации само по себе не является подтверждением его реализации. Результаты запусков, проверенные версии и ограничения испытаний записываются в отдельные отчёты.

## 1. Область применения

**VL Model Package (VLMP)** — часть семейства **VL Exchange**, переносимый модельный узел, включающий веса, Python-код подготовки входа и обработки выхода, метаданные, точное отображение классов и проверочные примеры. В первоначальном документе рассматривалась цепочка модель → блок → сценарий. Это историческая схема, а не актуальное требование: межвендорный обмен использует VLMP/VLSP, VLBP остаётся внутренним форматом VL. Их собственные спецификации, графы блоков, правила, состояние сценария, трекинг и работа с камерами не входят в VLMP v0.1.

Обязательный профиль этой редакции:

- интерфейс пользовательской Python-модели `python-custom-v1`;
- профиль исполнения `inline_cpu_onnx_fp32`, backend ONNX Runtime с `CPUExecutionProvider`;
- классификация одного изображения, один вход и один выход, статические тензоры, batch = 1;
- вход модели float32 NCHW; выход inference float32 NC; итоговый результат `Classification`.

TensorRT, CUDA-инференс, Torch inference, TensorFlow, динамические тензоры, детекции, сегментации и последовательности изображений не являются обязательными возможностями v0.1. Их наличие в прежнем `model_info.json` сохраняется. Оно не означает, что эти возможности проверены новым пилотом.

Поддержка пакета всегда утверждается для **конкретного пакета, профиля и окружения**. Диапазон opset в схеме не подтверждает успешное исполнение всех ONNX-операторов этого диапазона.

## 2. Сохранение существующего пакета

Существующие `__init__.py`, `model.py`, `model_info.json`, `coco_categories.json`, вспомогательные модули и веса ДОЛЖНЫ сохранять свои байты и прежние точки входа. Новые поля НЕ ДОЛЖНЫ добавляться в legacy JSON ради соответствия этой спецификации. Новые требования описываются в отдельном `model-package.json`.

Основная совместимая поставка — внешний wrapper:

```text
package-root/
├── model-package.json
├── artifacts/                 # прежняя директория модели, без изменения файлов
│   ├── __init__.py
│   ├── model.py
│   ├── model_info.json
│   ├── coco_categories.json
│   ├── custom_modules/        # если требовались прежней модели
│   └── weights*.onnx
└── golden/                    # проверочные входы, за пределами legacy artifacts
    ├── black.npy
    ├── red.npy
    └── blue.npy
```

Имя директории `artifacts` не обязательно; её положение задаёт `entrypoint.root`. Размещение sidecar непосредственно внутри прежней директории МОЖЕТ применяться только после отдельной проверки, что соответствующий legacy loader принимает дополнительный файл. Результат такой проверки нельзя предполагать по этой спецификации.

Box5 получает прежнюю директорию, а не обязан разбирать wrapper или новый manifest. Адаптер к Box5 МОЖЕТ прочитать manifest, проверить его, затем передать прежнюю директорию существующему загрузчику. Такой адаптер не должен заменять существующий inference backend собственной реализацией при проверке совместимости с Box5.

## 3. Manifest и идентичность поставки

Manifest — строгий UTF-8 JSON по [model-package.schema.json](model-package.schema.json). Комментарии, дублирующиеся JSON-ключи, NaN и Infinity недопустимы. Неизвестные поля вне `extensions` отклоняются.

| Поле | Нормативное значение |
|---|---|
| `format` | `vl.model-package` |
| `spec_version` | `0.1.0`, версия нового формата, а не версия модели или SDK |
| `name`, `version` | Имя и версия поставки; версия пакета не обязана совпадать с legacy `model_version` |
| `entrypoint` | Legacy root, `model.py`, класс `Model`, протокол и точная версия SDK |
| `legacy` | Точные пути прежних metadata/categories JSON |
| `files` | Полная таблица `относительный путь → SHA-256 байтов файла` |
| `profiles` | Точный файл весов, backend, типы, формы и имена тензоров |
| `dependencies` | Явно используемые моделью Python distributions и ограничения их версий |
| `source_input` | Семантика исходного изображения до `preprocess` |
| `result` | Тип результата и отображение output index / category ID / label |
| `required_capabilities` | Возможности, без которых пакет нельзя исполнить |
| `golden` | Проверочные входы, ожидаемые результаты и допуски |
| `extensions` | Расширения в отдельных пространствах имён |

Все пути ДОЛЖНЫ быть относительными POSIX-путями без `..`, `.`, абсолютных префиксов, обратной косой черты, пустых сегментов и glob-шаблонов. Ссылки и выход за границу package root запрещены. Корректность одного только регулярного выражения схемы недостаточна: требуется проверка фактического разрешения путей.

`files` ДОЛЖЕН перечислять каждый обычный файл поставки, кроме самого `model-package.json`, включая все Python-модули, дополнительные веса и golden inputs. Неперечисленные, пропавшие, изменившиеся файлы и symlinks отклоняются. `entrypoint.root/__init__.py`, `entrypoint.root/model.py`, оба legacy JSON и выбранные веса обязательны. Отчёты и кэш интерпретатора сохраняются за пределами пакета.

Идентичность испытанной поставки подтверждается SHA-256 исходных байтов manifest и совпадающими digest всех его файлов. Исполнитель ДОЛЖЕН проверить digest до импорта Python-кода, не изменять файлы и не писать `__pycache__` внутрь пакета. Контрольные суммы подтверждают целостность и равенство байтов; аутентичность автора этим форматом не устанавливается.

## 4. Legacy metadata и выбор весов

Пути `legacy.model_info` и `legacy.categories` ДОЛЖНЫ указывать на `model_info.json` и `coco_categories.json` в `entrypoint.root`. `model_type` ДОЛЖЕН быть `custom_model`, `task_type` — `image_classification`; выбранный `inline_cpu_onnx_fp32` должен присутствовать в legacy `deploy_profile.profiles`, а legacy `default_profile` — принадлежать тому же списку.

Новый manifest не изменяет default legacy profile: для этого пилота исполнитель явно выбирает CPU-профиль. Никакой автоматический переход на GPU, другой backend, другие веса или точность не допускается.

`profiles[0].weights` — **один точный файл**, включённый в `files`. Legacy `weights_path` может оставаться прежним glob. Manifest однозначно выбирает соответствующий ему файл. Если legacy loader выбирает веса самостоятельно, адаптер ДОЛЖЕН проверить, что он выбрал именно этот файл. Неоднозначный выбор отклоняется до inference.

Высота и ширина из `model_info.img_size` ДОЛЖНЫ совпадать с H/W входного тензора manifest и ONNX-графа. Имена `input_names` совпадают с ключами результата `preprocess` и входами графа; `output_names` — с выходами графа и ключами аргумента `postprocess`. Порядок именованных выходов не должен зависеть от неоговорённого порядка обхода контейнера.

## 5. SDK, зависимости и backend

Интерфейс `python-custom-v1` фиксирует следующие методы и атрибуты:

```python
class Model:
    input_names: Sequence[str]
    output_names: Sequence[str]
    def __init__(self, **model_attributes: int | float | str | bool | None): ...
    def preprocess(self, data: NDArray) -> Mapping[str, NDArray | torch.Tensor]: ...
    def postprocess(self, outputs: Mapping[str, torch.Tensor],
                    categories: Sequence[str]) -> Classification: ...
```

`Classification` — прежний тип `vlmodels_types.Classification` с полями `label: str`, `score: float`. Его поля и вызовы модели не расширяются нейтральными `category_id`/`output_index`: они добавляются внешним сериализатором результата.

В manifest ДОЛЖНА быть указана точная версия `entrypoint.sdk.version`. Изменение установленной SDK не считается автоматически совместимым. Совместимость с другим SDK требует отдельной записи и повторного прогона. Для текущего пилота исходный проверяемый интерфейс — SDK `vlmodels-types 1.8.1`; это не утверждение, что старая документация с примером 1.5.0 описывает актуальное развёртывание.

`dependencies` описывает зависимости самого `model.py` и его вспомогательных модулей. `version_specifier` — непустое ограничение PEP 440, проверяемое по фактическим установленным distributions. Имя distribution нормализуется по правилам Python packaging. Зависимости SDK и inference backend проверяются отдельно; backend МОЖЕТ предоставляться distribution `onnxruntime` или `onnxruntime-gpu`, если реально используется `CPUExecutionProvider`. В отчёт записываются фактические distribution, версии, Python и providers. Широкий допустимый диапазон зависимости не является доказательством тестирования всех версий из этого диапазона.

Пакет не устанавливает зависимости во время импорта или inference и не изменяет `sys.path`. Внутрипакетные импорты относительные, например `from .custom_modules import utils`. Внешние импорты установленных зависимостей обычные, например `import numpy`.

Профиль использует ONNX с одним тензорным входом float32 `[1,3,H,W]` и одним выходом float32 `[1,C]`, все размерности — положительные фиксированные целые. ONNX external data и custom operator domains не входят в v0.1; валидатор их отклоняет. Допускается стандартный domain `""` / `ai.onnx`. Manifest явно объявляет opset 7–15 и он совпадает с импортом стандартного domain графа. Исполнитель обязан проверить ONNX-граф и возможность загрузки его конкретным backend. Текущий smoke target — opset 13, IR 8; успех на нём не подтверждает все прочие opset/операторы.

## 6. Исходное изображение и inference-тензоры

Вход `preprocess` — один C-contiguous NumPy ndarray с dtype `uint8`, формой `[H_source,W_source,3]`, H/W > 0 и порядком каналов **BGR**. Значения — целые 0–255. Начало координат изображения в левом верхнем углу, первая ось — строки, вторая — столбцы. Alpha-канал и implicit RGB conversion не допускаются. Размер исходного изображения может отличаться от фиксированного размера inference-тензора: преобразование выполняет `preprocess`.

`preprocess` самостоятельно задаёт преобразование BGR→RGB, нормализацию, resize/crop и иной алгоритм, если он нужен конкретной модели. Этот алгоритм является частью поставки через неизменяемый Python-код. Исполнитель НЕ ДОЛЖЕН добавлять свои цветовые преобразования, нормализацию или resize. Golden tests ДОЛЖНЫ включать различающиеся по каналам входы, чтобы выявлять неверный BGR/RGB порядок.

Результат `preprocess` содержит ровно объявленные входные имена. Допускаются CPU NumPy arrays или CPU torch tensors; каждый вход после нормализации представления имеет ровно объявленные dtype и shape. Молчаливое приведение float64/float16 к float32 или иной формы к требуемой запрещено. Уплотнение памяти без изменения значений разрешено. Все числа должны быть конечными.

Backend исполняет выбранный граф на CPU. Его выходы проверяются по именам, dtype и форме, затем передаются в `postprocess` как `Mapping[str, torch.Tensor]` на CPU. Допускается создание torch view/copy поверх NumPy без изменения чисел. Выход inference может представлять logits или probabilities: их интерпретация принадлежит поставляемому `postprocess`.

## 7. Категории и итоговый результат

Число C в выходной форме равно количеству legacy `categories.categories` и элементов `result.category_map`. Для каждого i = 0…C−1:

- `category_map[i].output_index == i`;
- `category_map[i].label == legacy.categories.categories[i].name`;
- `category_map[i].category_id == legacy.categories.categories[i].id`.

Порядок legacy массива **не сортируется по `id`**. Category ID — независимый идентификатор метаданных; он может иметь пропуски и не равен индексу output tensor по определению. ID и label уникальны в пакете. Для `postprocess` передаётся `tuple(category['name'] for category in categories['categories'])` в прежнем порядке.

В обязательном профиле классификации нет фильтра, скрывающего выбранный класс после `postprocess`. `exclude` ДОЛЖЕН быть false для всех категорий. Legacy per-class `threshold`, цвета, локализации и `is_violation` сохраняются как метаданные и не добавляют неявной обработки исполнителем. Если конкретная модель применяет пороги, этот алгоритм должен быть реализован её кодом и отражён в golden outputs.

Результат модели должен содержать label из таблицы и конечный score в [0,1]. Внешний сериализатор находит единственное отображение по label и выдаёт:

```json
{"results":[{"label":"red","score":0.5761168847658291,"category_id":1,"output_index":0}]}
```

Envelope соответствует [classification-result.schema.json](schemas/classification-result.schema.json). Для одного входа возвращается ровно один результат. Неизвестный label, отсутствующий score, NaN, Infinity и score вне [0,1] — ошибка, а не пустой результат. Выбор класса, softmax и разрешение равных максимальных значений принадлежат коду модели. Демонстрационный классификатор использует argmax с выбором минимального output index при равенстве; это не навязывается всем будущим моделям без отдельного интерфейса.

## 8. Конструктор, состояние и жизненный цикл

Conformance run использует **только defaults** из прежнего `model_info.model_attributes`: каждый атрибут должен иметь допустимый scalar type и `default` соответствующего типа. Все defaults передаются как keyword arguments в `Model` без изменения значений. Пустое или отсутствующее поле означает отсутствие kwargs. Ненулевой внешний override не входит в этот тест; для legacy loader он заменяет словарь defaults целиком, а не объединяется с ним. Исполнитель не должен незаметно вводить иную семантику merge.

Порядок действий: проверка структуры/версий/digest → проверка зависимостей → импорт изолированного Python-пакета → создание `Model` → инициализация CPU backend → последовательные predict → освобождение backend и модели. В legacy интеграции используются существующие операции initialize/predict/release. Новый обязательный метод `close` в `Model` не вводится.

На одном экземпляре не допускаются пересекающиеся predict. Один вызов — полностью preprocess → inference → postprocess, прежде чем начинается следующий. Это сохраняет совместимость с моделями, хранящими размер изображения между этапами. Состояние экземпляра не разделяется с другими экземплярами.

В v0.1 итог классификации не должен зависеть от истории предыдущих изображений. Golden tests запускаются в прямом и обратном порядке на новых экземплярах, а один вход повторяется после другого. Ошибка вызова завершает текущий вызов; повторный запуск требует нового экземпляра, если исполнитель не доказал безопасное восстановление. Освобождение ресурсов выполняется и после ошибки. Исполнитель не подменяет ошибку результатом предыдущего запроса.

Изолированный namespace — изоляция импортов, а не обещание процессной или аппаратной изоляции. Исполнение Python является исполнением кода пакета; статическая валидация не импортирует этот код. Процессная изоляция и эксплуатационные политики объявляются реализацией отдельно и не выдаются за проверенные свойства legacy loader.

## 9. Ошибки и расширения

Ошибки manifest/version/digest/path/dependency/required capability обнаруживаются до импорта модели. Ошибки графа, input/output contract и исполнения не должны приводить к fallback на другую модель/точность/backend.

Машинный отчёт об ошибке ДОЛЖЕН содержать стабильный код/класс ошибки и сообщение; отдельное поле стадии валидации/загрузки/исполнения рекомендуется. Внутренние имена классов исключений могут отличаться. CLI возвращает ненулевой exit status; API возбуждает исключение или возвращает отдельный тип ошибки. Ошибка не соответствует успешному result envelope.

`required_capabilities` обязательно включает `python-custom-v1`, `onnx-cpu-fp32`, `classification-v1`. Любая нераспознанная обязательная capability отклоняется. Расширения имеют reverse-DNS ключ и объект `{ "required": boolean, "data": ... }`. Неизвестное расширение с `required:true` отклоняется до импорта. Неизвестное optional расширение сохраняется без интерпретации и не влияет на обязательный профиль. Optional extension не может менять смысл обязательных полей; для этого требуется новая версия интерфейса или обязательная capability.

## 10. Golden tests и критерии соответствия

В пакете минимум три различных golden input. Каждый — `.npy`, загружаемый без pickle, с допустимым BGR uint8 HWC изображением. ID и пути fixtures уникальны, содержимое минимум трёх входов различается. Входы включены в `files`. Ожидаемый канонический результат хранится в manifest. В демонстрации используются black и разные цветовые каналы; рекомендуются также неоднородное изображение и изменение исходного H/W, если код выполняет resize.

Label, category_id и output_index совпадают **точно**. Для score выполняется:

```text
abs(actual_score - expected_score) <= atol + rtol * abs(expected_score)
```

Все значения конечны. В v0.1 0 ≤ atol,rtol ≤ 0.001; для демонстрации рекомендуются atol=1e-6, rtol=1e-5. Допуски выбираются до испытаний и входят в digest manifest; нельзя расширять их после неуспешного результата без новой версии пакета. Успешное совпадение top-1 без проверки score недостаточно.

Проверка включает все fixtures, повторные вызовы, изменение порядка и повторное создание экземпляра. Отрицательные проверки включают изменённый digest, отсутствующий файл, неверный shape/dtype, неизвестную required capability/extension, неверное отображение категорий и неподдерживаемый профиль.

Утверждение «один пакет работает в двух независимых исполнителях» требует:

1. совпадающей идентичности manifest и всех файлов в обоих испытаниях;
2. отдельного пути загрузки и управления inference в каждом исполнителе;
3. одного и того же пакета и профиля, без правки model.py/JSON/весов между запусками;
4. всех golden результатов в заданных допусках;
5. отчёта о Python/SDK/backend/dependencies/providers, версиях исполнителей и ограничениях каждого теста.

Общая ONNX Runtime библиотека и общий SDK типов допустимы: независимость означает разные интеграции/загрузчики, а не два разных математических inference engine. Два CLI, вызывающие один и тот же адаптер, не доказывают эту независимость. Совместимость с Box5 подтверждается только отдельным запуском его реального loader; анализ исходного кода или нейтральный runner этого запуска не заменяют. Испытание в изолированном процессе/контейнере с текущими библиотеками Box5 не равно production deployment.

Это проверка переносимости модельного узла на выбранных входах. Она не устанавливает качество реального детектора, переносимость целого сценария, универсальную поддержку любого Python-кода или совместимость других backend profiles.
