# Экспериментальный снимок разрешения для асинхронного вызова

Этот документ описывает дополнительный экспериментальный формат reference-реализации. Он не является обязательным для всех host и не представляет межъязыковой стандарт канонизации. Общие требования защищённой поставки описаны в [VL Exchange Security](../../../docs/security/SPECIFICATION.ru.md).

Референсная дополнительная возможность `vl.exchange.execution-lease` v0.1.0 позволяет доверенной очереди сохранить исходное разрешение между обращением к сервису и фиксацией ответа, в том числе при перезапуске процесса. `capture_persistent_lease(binding, installation_signing_key)` создаёт JSON со строго заданными полями: `format`, `version`, `binding`, `mode`, `license`, `license_signature`, `grant` и `signature`. Значения `license` и `license_signature` содержат подписанные публичные байты лицензии в Base64; `grant` равен null для offline или содержит `raw`, `signature`, `nonce` исходного подписанного online grant. Закрытый ключ и корни доверия не помещаются в снимок.

Все поля кроме `signature` сериализуются эталонной реализацией как UTF-8 JSON с сортировкой ключей, разделителями `,` и `:` и без NaN; подпись Ed25519 делается закрытым ключом установки с доменом `VL-EXCHANGE-PERSISTENT-LEASE-V1` и байтом 00. Публичный ключ установки берётся из подписанной издателем лицензии, а ключи издателя и сервера — только из конфигурации принимающего host. Этот формат является экспериментальным JSON для Python-эталона, не объявляется межъязыковым стандартом канонизации.

`binding` — ограниченная непустая строка с identity конкретной операции. Сама очередь обязана надёжно связать снимок с точным `job_id` и неповторимым `attempt_id` и передать ожидаемый binding отдельно; брать ожидаемое значение из проверяемого снимка недостаточно. При восстановлении host вновь авторизует конкретную установку и пакет, сверяет неизменную подписанную лицензию, проверяет подпись установки, операционную привязку, исходный grant и его срок. Принятие более нового grant само по себе не продлевает исходный. Очередь должна получить отдельный свежий снимок на dispatch и сохранить его вместе с выбранной попыткой, затем проверять его непосредственно перед внешним вызовом и перед фиксацией результата. Лицензия, полученная при постановке в очередь, может истечь до dispatch и не заменяет этот новый снимок. Обработка результата сценарием — новая операция со своим разрешением.

Для контроля целостности исторической постановки доступен `assert_persistent_lease_integrity(snapshot, binding)`: он проверяет оригинальные подписи и binding даже после истечения grant постановки, при наличии текущего валидного доступа к этой же лицензии. Он не авторизует вызов MLLM или фиксацию ответа; там необходимо проверять отдельный актуальный снимок через `assert_persistent_lease`. Подпись установки не является независимой отметкой времени подписания, поэтому доверенный host, защита часов и контроль отката хранилища остаются необходимыми.

Этот механизм не обеспечивает защиту от подмены trusted runtime/администратора, отката доверенных часов или одновременного отката всей базы вместе с ранее действительными job/attempt/snapshot. Защита хранилища и запрет повторного применения обеспечиваются очередью. В online режиме отзыв становится известен при обращении к лицензирующему серверу или не позднее истечения выданного grant; без сетевого обращения мгновенный отзыв не гарантируется.

Для рабочего соединения требуется HTTPS с проверкой сертификата и имени сервера. HTTP разрешён только для явно включённого теста loopback. Перенаправления запрещены. Недоступность сервера, недействительная подпись или неподходящий grant блокируют новый вызов. Полученный grant нельзя переиспользовать для другого nonce, установки, лицензии или пакета.
