# VLSP 0.2 — проверка входной очереди

Это архив результатов локального экспериментального стенда от 2 ноября 2026 года. Портированные исходники адаптера и инструкция по повторному запуску доступны отдельно в [пилоте VideoPipe](../videopipe-pilot/README.md). Сборка требует внешних зависимостей; численные результаты зависят от окружения. Исходный VideoPipe собирался на commit `2a3b461e555725681ec2c0b3693e743e10408299`.

Профиль `vlsp.stream-policy.v1` был реализован отдельно для reference executor и для независимого host VideoPipe. Один и тот же ZIP SHA-256 `1461028eb6176c72bb0229eb8b28b7e697b6a4fcc1f7d420e095631bf4e0f332` использован без изменения. Запущены реальные CPU ONNX детектор и два разных классификатора и чистый IoU tracker.

**Результат: 12 сценариев проверки прошли на обоих host.** Во всех шести сочетаниях трёх правил перегрузки и двух способов остановки совпали результаты, состояния, учёт кадров и вызовы моделей. Также проверены timeout и повтор подачи непринятого кадра, освобождение до deadline, изоляция источников, повторное открытие очереди с сохранением состояния сценария и отсутствие commit после ошибки модели. При потере ответа после commit оба host сообщают о неизвестном результате фиксации. На пути VideoPipe дополнительно проверено, что закрытие во время обработки отклоняется до завершения принятого кадра.

| Политика | Заполненная очередь, `drain` | Заполненная очередь, `discard` |
|---|---|---|
| `block` | Кадр сверх лимита получает явный timeout; принятые выполняются | Ожидающие кадры отмечаются как отброшенные; выполняемый завершается |
| `drop_oldest` | Старый ожидающий кадр явно отброшен, новый обработан | Оставшиеся ожидающие кадры явно отброшены |
| `drop_newest` | Новый кадр явно отброшен, ранее принятые обработаны | Оставшиеся ожидающие кадры явно отброшены |

Емкость считает ожидающие кадры; дополнительно может выполняться один вызов. На каждую подачу выдаётся отдельный Future со статусом `committed`, `dropped`, `rejected` или `error`. Учитываются причины потерь, отклонения и глубина. State/order/events не меняются для кадров, которые не дошли до `process`. Несколько source/run используют общий lock экземпляра сценария. Тестовый gate специально удерживает первый вызов, чтобы проверка переполнения была воспроизводимой; gate не заменяет реальные вычисления принятых кадров.

## Нагрузка на синтетическом стенде

Для последовательного `block` с очередью на четыре ожидающих кадра каждый host принял и обработал **120 из 120 кадров без потерь**, с одинаковыми событиями и состоянием. Отдельный залп `drop_oldest`: каждый host получил 300 кадров; reference обработал 5 и явно отбросил 295, VideoPipe обработал 23 и отбросил 277. Различие числа пропусков зависит от темпа подачи, планирования и IPC: этот залп не является сравнением производительности двух движков.

Для этих 120 крошечных кадров 4×2 на CPU в данном запуске получено около 192 кадров/с у reference и 153 кадров/с у VideoPipe с Python IPC. p95 от поступления в worker до начала callback — около 27,8 мс и 35,4 мс; p95 вызова Python Session — около 5,0 мс и 6,2 мс. Это измерения **только синтетического локального стенда**, не оценка промышленной производительности, реальных потоков или работы GPU. Полные данные, p50/p95/p99 и исходы: [stream-load.json](stream-load.json).

Всего через нативный граф VideoPipe переданы 464 тестовых кадра. Native source создаёт `vp_frame_meta` и `cv::Mat`; callback получает повторно сериализованные байты из этого объекта. Для каждого успешно обработанного кадра сверены SHA-256 данных и фактические вызовы всех трёх ONNX-графов. Чистота реализации проверяется import guard: independent host не загружает reference scenario runtime.

## Границы и воспроизведение

Ограниченная очередь находится в Python worker **перед сценарием**, после прохождения кадра через VideoPipe. Внутренние upstream очереди VideoPipe этой реализацией не ограничиваются. `max_queue_frames` не ограничивает память, занятую несколькими параллельно заблокированными отправителями, а также память самого VideoPipe. При потере IPC или неструктурированном исключении после возможного commit результат может быть неизвестен; это не доказательство rollback или exactly-once.

Проверены реальные offline grant и защита ZIP, но не RTSP/кодеки, GPU, длительный production workload, внешняя доставка или crash recovery. Производственный профиль host требует отдельных измерений и испытаний. JSON Schema проверяет структуру политики; целочисленное представление `max_queue_frames` и `max_wait_ms` проверяется host дополнительно: `1.0`, `1e0` и boolean отвергаются.

Полная регрессия: 142 теста прошли — [stream-pytest.txt](stream-pytest.txt). Базовый строгий VLSP прогон после изменений — 115/115 сравнений, 28 ошибок с идентичными кодами и флагами: [comparison.json](comparison.json).

Прогон сохранил хеши применённых исходников, бинарника VideoPipe и пакета. Пути исходников в JSON относятся к первоначальному рабочему дереву, а не к расположению файлов в данном репозитории. Режимы перегрузки и остановки также проверены отдельными детерминированными модульными тестами с тестовым callback; они не выдаются за настоящие model inference calls.
