# VL Model Package 0.2.0 — классификация и детекция

**Статус: финальная редакция спецификации проекта VL Exchange 0.2.0.** Эта редакция определяет общую оболочку и два явно согласуемых профиля. Её публикация не означает отраслевого утверждения, совместимости конкретной платформы или готовности реализации к промышленной эксплуатации. MUST / ДОЛЖЕН, MUST NOT / НЕ ДОЛЖЕН и MAY / МОЖЕТ обозначают требования, запреты и возможности. Результаты конкретного испытания указываются отдельно.

Выпуск включает `classification-onnx-cpu-v1` и `detection-onnx-cpu-v1`. Оба профиля ограничены ONNX Runtime, CPU, FP32, одним статическим входом и batch=1. Ограничения относятся к этим профилям; поддержка GPU, динамических размеров, другого backend, сегментации, MLLM и произвольных нейросетей данной редакцией не заявляется. Будущие профили требуют отдельно опубликованного контракта и проверки возможностей host. Модель классификации и детектор имеют разные результаты; общая оболочка не делает их результаты взаимозаменяемыми.

## 1. Пакет и манифест

Пакет — ZIP или проверенная неизменяемая директория с `model-package.json` в корне и файлами, точно перечисленными в `files`. Поддерживающий host ДОЛЖЕН принимать ZIP; поддержка директории необязательна и объявляется отдельно. Манифест является strict UTF-8 JSON без повторяющихся ключей, комментариев, NaN и Infinity, соответствует [схеме](model-package.schema.json), содержит `format="vl.model-package"` и точный `spec_version="0.2.0"`. Неизвестные основные поля и неподдерживаемый профиль отклоняются. `model_id` и `version` идентифицируют поставку; одну и ту же пару не переиздают с другими байтами. SHA-256 точных байтов манифеста и SHA-256 полного ZIP фиксируются отдельно.

Для всех целочисленных полей, включая размеры, opset, индексы и ID, требуется целочисленное представление JSON без дробной или экспоненциальной записи; `1.0`, `1e0` и boolean отклоняются. JSON Schema проверяет математический тип и не обеспечивает это правило самостоятельно: host обязан дополнительно проверить исходное представление при разборе.

Общие поля:

| Поле | Назначение |
|---|---|
| `profile` | Точный `classification-onnx-cpu-v1` или `detection-onnx-cpu-v1` |
| `backend` | Engine, устройство, точность, путь ONNX, opset, имя/форма входа и имена выходов |
| `source_input` | Формат исходного изображения и точная форма `[H,W,3]` |
| `categories` | Массив `{output_index,category_id,label}` |
| `result` | Тип и, для детекции, правила фильтрации и координат |
| `golden` | Численные допуски и не менее трёх ожидаемых результатов |
| `files` | Относительный путь → SHA-256 точных байтов каждого файла, кроме самого manifest |
| `required_capabilities`, `extensions` | Обязательные возможности и расширения с полями `required` и `data` |

Категории имеют уникальные `category_id` и `label`; `output_index` равен позиции записи в массиве, начиная с нуля. `source_input.shape` обязан совпадать с `[backend.input_shape[2], backend.input_shape[3], 3]`. Имена входа и выходов не пусты; у детектора имена выходов попарно различны. Весовой файл и каждое изображение из `golden` ДОЛЖНЫ входить в `files`. Идентификаторы и пути golden уникальны; как минимум три входа различаются по содержимому массива с учётом dtype, формы и значений. Допуски `atol`, `rtol` устанавливает издатель до запуска, каждый в диапазоне `[0,0.001]`. Численные значения сравниваются по `abs(actual-expected) <= atol + rtol*abs(expected)`; строки, ID, число объектов и порядок сравниваются точно.

Golden input использует формат NPY версии 1.0, 2.0 или 3.0 и содержит только `uint8` массив точно заявленной формы `source_input.shape`. До выделения памяти host проверяет заголовок размером не более 10 000 байт, dtype и ограниченные размеры; длина payload обязана равняться `H×W×3` байтам. Object dtype, pickle, усечённый файл и лишние байты запрещены; при использовании NumPy загрузка выполняется с `allow_pickle=False`. C- и Fortran-порядок массивов допускаются.

Ожидаемый результат каждого golden ДОЛЖЕН соответствовать объявленным категориям и правилам выбранного профиля. Для классификации его `category_id`, `label` и `output_index` должны указывать на одну и ту же запись `categories`. Для детекции каждый ожидаемый `category_id` и `label` должны совпадать с категорией, `score` должен быть не ниже порога, `bbox` должен иметь корректные границы, а `object_id` — каноническое неотрицательное десятичное число из ASCII-цифр без ведущих нулей, меньше `max_detections`. Индексы ожидаемых детекций должны строго возрастать, повторять ID нельзя. Host ДОЛЖЕН отклонить несогласованные golden до инференса; корректность самих ожидаемых значений относительно графа проверяется отдельным исполнением golden.

`required_capabilities` включает `onnx-cpu-fp32` и точное имя профиля. Host НЕ ДОЛЖЕН запускать пакет, если не поддерживает обязательную capability или расширение `required=true`. Неизвестное необязательное расширение MAY игнорироваться без изменения обязательного поведения. Проверка манифеста сама по себе не доказывает инференс.

## 2. Проверка ZIP, файлов и графа

Пути файлов относительные, канонические POSIX: для переносимости между ОС запрещены двоеточие в любом сегменте, абсолютный путь, путь с буквой диска (`C:/...`, `C:relative`), обратная косая черта, пустой сегмент, `.`/`..`, NUL, symlink, специальные файлы, повторяющиеся имена ZIP и файлы вне `files`. Извлечение не выходит за выделенный каталог. Host отклоняет архив свыше 128 МиБ, более 1024 записей или свыше 512 МиБ распакованных данных, а также отдельный файл свыше 128 МиБ; дополнительные лимиты host должны приводить к явному отказу. До открытия графа проверяются каждый путь, полный inventory, размеры и SHA-256. Файл, manifest и граф не должны подменяться после проверки. При обращении к директории действуют те же ограничения на inventory, symlink и размеры.

Host отклоняет внешние данные весов ONNX и локальные ONNX functions, проверяет корректность графа, заявленный opset и точные типы/формы/имена ONNX входа и выходов до исполнения. В этих двух профилях `opset_import` содержит ровно одну запись стандартного домена `""` с версией 13; домен узла, включая вложенные графы, — `""` или `"ai.onnx"`; custom domains/operators не поддерживаются. Поддерживаются только один `float32 [1,3,H,W]` input, `1 ≤ H,W ≤ 4096` и CPU execution provider. `H` и `W` задаются пакетом, а не фиксируются значением демонстрации. Исполнение необъявленного Python-кода пакета данными профилями не требуется. Проверки целостности не заменяют подпись, права или изоляцию; для защищённой поставки применяется отдельный [security profile](../../../../docs/security/SPECIFICATION.ru.md).

## 3. Общий вход и подготовка

Вход в `infer` — `numpy.ndarray` изображения `uint8 [H,W,3]` в BGR, размеры строго совпадают с `source_input.shape`; неявное преобразование иных типов в массив запрещено. Входной массив MAY быть несмежным в памяти; подготовленный тензор является C-contiguous. Host НЕ ДОЛЖЕН молча менять размер, dtype, цвета или принимать пакет с несоответствующим графом. Если нужно resize/crop исходного кадра, его выполняет вызывающая сторона и отдельно сохраняет преобразование координат. Для модели host преобразует BGR→RGB, транспонирует HWC→NCHW, добавляет batch и преобразует значения в float32, деля на 255. Нормализованные координаты детектора относятся к переданному в `infer` изображению, не автоматически к исходному кадру.

## 4. Классификация

`backend.outputs` содержит только `scores`: имя единственного ONNX выхода `float32 [1,C]`, где `C` равно числу категорий. Значения конечны, находятся в `[0,1]`, а их сумма отличается от 1 не более чем на `0.0001`. Это вероятности, не произвольные logits. Неверная форма, тип или значения — ошибка. Результат `vl.classification.v1` имеет точный вид `{label,score,category_id,output_index}`. `output_index` — индекс максимальной вероятности; при равенстве выбирается первый индекс. Label и ID берутся из соответствующей категории.

## 5. Детекция

`backend.outputs` содержит `boxes`, `scores`, `classes`: имена трёх выходов ONNX `float32 [1,N,4]`, `float32 [1,N]` и `int64 [1,N]`, где `N=result.max_detections`, `1 ≤ N ≤ 1000`. В `result` указываются `type="vl.detections.v1"`, `threshold` от 0 до 1 и `bbox_space="normalized-xyxy-input-frame"`. Все score конечны и лежат в `[0,1]`; host сохраняет строки со score больше либо равным порогу, в исходном порядке. Выходной `object_id` равен десятичному индексу строки ONNX до фильтрации и уникален только в одном результате. У каждой сохранённой строки category ID должен быть объявлен; конечный `bbox=[x_min,y_min,x_max,y_max]` лежит в `[0,1]` и удовлетворяет `x_min < x_max`, `y_min < y_max`. Label берётся из категории. Пример результата: `{"detections":[{"object_id":"0","label":"person","category_id":1,"score":0.9,"bbox":[0,0,1,1]}]}`; отсутствие объектов — пустой массив. NMS и упаковка выходов выполняются графом; этот профиль не задаёт интерпретации raw выходов других детекторов.

## 6. Совместимость и доказательство

`0.2.0` — новый manifest и новый digest; он не объявляется автоматически совместимым с ранее опубликованными `0.2.0-draft.1` или `0.2.0-detection-draft.1`. Существующие ZIP, схемы и загрузчики остаются отдельными. Host, заявляющий поддержку старой версии, проверяет её по соответствующему старому контракту; неизвестную версию отклоняет до выполнения. Миграция в новый manifest создаёт новый ZIP и новые хеши. Защищённой поставке нужны новые подписи и разрешения; сценарий, зафиксировавший старый digest model manifest, требует явно обновлённой привязки.

Для подтверждения переносимости каждого профиля один неизменённый ZIP запускается на двух независимо реализованных host; host проверяют golden, все входы и результат в зафиксированных допусках, ошибки и совместимость старых пакетов отдельно. Общие сторонние библиотеки, модель, ограничения и среда указываются в отчёте. Тестовые модели синтетические и необученные: результат не является измерением качества промышленной аналитики или поддержки сторонней платформы.
