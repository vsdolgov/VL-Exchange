# Protected delivery of VLMP 0.2.0 models

**English | [Русский](PROTECTED-DELIVERY.ru.md)**

This document specializes the existing [VL Exchange Security 0.1 profile](../../../docs/security/SPECIFICATION.en.md) for the VLMP 0.2.0 classification and detection profiles. It does not introduce a new model-manifest schema or change the bytes of an existing package. A deployment explicitly selects protected or unprotected delivery; support for VLMP 0.2.0 alone does not imply that a host implements protected delivery. The operator configures trusted issuer keys, recipient/installation credentials, policy and, for online use, the server endpoint and verification key outside the package.

## Binding to a model package

The protected envelope contains the encrypted **exact original VLMP ZIP** and a signed execution license. For a VLMP 0.2.0 package the signed claims MUST bind `package_format` to `vl.model-package`, `manifest_path` to `model-package.json`, `manifest_sha256` to the exact original manifest bytes and `package_sha256` to the exact original ZIP bytes. The signature authenticates these claims; a ciphertext hash alone is not publisher authentication. The receiving host MUST validate the recipient, policy, signature, license interval and execute permission, decrypt, verify the signed ZIP/manifest digests and format, and validate the full VLMP schema, inventory, file digests, profile and graph contract before executing or returning a prediction. Unknown profiles and mismatched package types are refused.

The model's identity in audit records is the signed original ZIP digest together with the signed manifest digest. If an implementation uses an extracted directory or an internal repackaging to load a model, it MUST preserve that identity separately, verify that the loaded manifest and file inventory are bound to the authorized package, and MUST NOT report the digest of a newly created ZIP as the digest of the original. Package files MUST remain unchanged from validation through use. An ONNX session loaded from validated graph bytes is not authorization to use the model after its lease has expired.

Model delivery is independent of a VLSP scenario's protected envelope. Encrypting or licensing the scenario alone does not protect separately supplied model ZIPs. Each model needs an envelope and entitlement for the receiving installation; a scenario's model-manifest digest binding is checked as well when the model is used by a scenario. A new license or recipient envelope can protect the same unchanged model ZIP; changing or repacking that ZIP changes its package digest and requires a new signed binding.

## Execution and lifecycle

For **offline** delivery, the host checks the signed entitlement and installation binding without a network request. Remote revocation cannot take effect immediately without an additional communication channel; the validity interval and local administrative controls apply.

For **online** delivery, a signed short-lived server grant bound to the license, installation, package and nonce is required before decryption. The host obtains and verifies fresh authorization as required before a call; request, signature, network, revocation or renewal failure MUST NOT silently fall back to offline. Operational online endpoints use HTTPS under the security profile; explicit loopback HTTP is limited to tests.

Before each prediction the host captures the authorization lease for that call. After inference and output validation, and **before returning or otherwise publishing the result**, it verifies that same lease is still valid. Expiry, revocation-related failure, closed authorization or a failed guard MUST NOT release a prediction. A newly issued grant MUST NOT retroactively authorize a result whose original grant expired during inference. The host closes the model and authorized package and releases temporary resources when the session ends, and cleans up if opening fails. The lease does not interrupt native ONNX inference, erase already exposed data, undo external actions or secure a compromised host.

## Verification expectations and limits

For each claimed model profile, tests should use the same unchanged ZIP in protected offline and online deliveries on each host, check real inference against expected results, record the original ZIP and manifest hashes, and compare outputs and rejection behaviour. Negative cases include expired or not-yet-valid licenses, wrong issuer/recipient/mode/permission, altered license, ciphertext, manifest or package, a mismatched model binding, unsupported profile, denied or revoked online grant, server/network failure, grant expiry while the license remains valid, license expiry, and expiry during inference before result publication. Rejected opening must not execute the model; a rejected call must not publish a prediction. Tests must distinguish faults actually exercised from profile requirements and must not use expired credentials or signatures generated for another ZIP as a positive result.

The reference security runtime is a prototype, not an attested or isolated execution environment. The administrator, clock, host and trust configuration are trusted. Secrets must not be embedded in packages or published in test logs. Plaintext may be present in a private temporary directory and process memory while a model is open; normal cleanup does not promise secure erasure or crash cleanup. Hardware-backed keys, independent rollback-resistant time, protection against host administrators, commercial licensing policy, real deployment key management, production server availability and model quality are outside this demonstration.
