# VL Model Package v0.2 — профиль детекции CPU ONNX

Статус: финальная редакция спецификации проекта VL Exchange от 03.11.2026. Прежний идентификатор manifest `0.2.0-detection-draft.1` остаётся pre-release и сохранён для совместимости без изменения байтов пакетов; статус документа не делает его финальной версией формата `0.2.0`. VLMP v0.1 сохраняет свой manifest и семантику без изменений; поддержка этого профиля не следует из поддержки v0.1. В публичном проекте есть отдельный профиль классификации `0.2.0-draft.1` с другой схемой manifest. Профиль детекции не заменяет его и не определяет общую схему; согласование семейств схем остаётся отдельной работой. Эта редакция определяет профиль `detection-onnx-cpu-v1` и результат `vl.detections.v1`. Финальная редакция проекта не означает утверждения отраслевым органом или готовности к промышленной эксплуатации. Возможности должны объявляться и согласовываться явно; неизвестный профиль отклоняется. VLSP по-прежнему не требует блоков, NRI или редактора VizorLabs.

Пакет включает `model-package.json` и перечисленные в `files` артефакты, включая ONNX веса и тестовые входы. Формат manifest — [JSON Schema](model-package.schema.json): strict UTF-8, без повторяющихся ключей, NaN/Infinity, незаявленных файлов и небезопасных путей. Идентичность — SHA-256 исходного manifest и полный inventory с SHA-256 файлов. Доверенный host проверяет их до загрузки и запрещает изменение между проверкой и использованием. SHA-256 не является лицензией или подписью; для защиты применяются отдельные механизмы VL Exchange Security. Веса отдельно поставляемой модели имеют отдельные права.

Профиль v0.2:

- Вход: один кадр NumPy совместимого вида, `uint8`, HWC, BGR, положительные размеры; manifest определяет точный статический размер. Batch = 1, CPU ONNX Runtime, float32, NCHW RGB. Кадр в этом профиле уже задан в размере модели; resize/crop остаются обязанностью host и их привязка к исходному кадру должна быть описана принимающей системой. Host выполняет преобразование BGR → RGB и масштабирование на 1/255.
- ONNX graph принимает один `float32 [1,3,H,W]` tensor и возвращает три tensor: boxes `float32 [1,N,4]`, scores `float32 [1,N]` и classes `int64 [1,N]`, N задан manifest, 1≤N≤1000. Число строк и имена задаются manifest. Координаты boxes уже нормализованы; category ID в classes обязан присутствовать в карте классов manifest. Отбор строк по порогу и отказ при невалидном выходе определены ниже. Распаковка и NMS выполняются внутри модели; этот профиль не подходит для raw outputs без такого адаптера.
- Результат `{"detections":[...]}` по [схеме результата](schemas/detections.schema.json). Каждая детекция содержит `object_id`, `label`, `category_id`, `score` и `bbox`.
- `bbox=[x_min,y_min,x_max,y_max]` в нормализованных долях изображения, переданного в `infer`, диапазон [0,1], начало координат в левом верхнем углу. Обязательно `x_min < x_max`, `y_min < y_max`. Если в `infer` передан crop, координаты относятся к crop, а для перевода в исходный кадр host обязан сохранить его преобразование. Демонстрация передаёт полный кадр без resize.
- `object_id` — непустая строка, уникальная внутри одного результата модели для одного кадра, без обещания стабильности между кадрами или моделями. Идентичность между кадрами назначает отдельный трекер. Результат пустого кадра — пустой массив.
- `score` — конечное число в [0,1]. Значение и критерий фильтрации объявляются моделью; оно не является гарантированной вероятностью. `label` и `category_id` берутся из зафиксированной карты классов, не угадываются принимающей системой.
- Лимиты, порядок результатов и способ разрешения конфликтов фиксируются профилем модели. Реализация ДОЛЖНА проверять фактическую форму/тип ONNX входа и выхода и не объявлять успешное исполнение по одному только прочитанному manifest.

Этот ограниченный профиль не определяет произвольные форматы изображений, переменный batch, генерализованное NMS, сегментацию, трекинг, GPU/TensorRT или качество детекции. Каждый slot с `score >= threshold` превращается в detection с `object_id` равным его десятичному индексу; остальные отбрасываются. Категории и boxes валидируются в каждом выбранном slot. Асинхронность, корреляция нескольких моделей, принадлежность crop/объекта и состояние трекера задаются отдельным профилем сценариев и host API. Ошибка выполнения модели не может молча превращаться в успешную пустую детекцию.

Пример — синтетический исследовательский ONNX с фиксированными слотами: оценка каждого слота реально вычисляется из красного канала изображения и параметра gain внутри ONNX, но модель не обучена и не определяет людей на реальном видео. Два независимых test inputs дают разные результаты. Он не является доказательством качества промышленной видеоаналитики. Доступный v0.2 reference host не является встроенным загрузчиком Box 5; совместимость с существующим v0.1 loader сохранена только для прежних v0.1 пакетов. Загрузка v0.2 в Box 5 и GPU требуют отдельной проверки и адаптера.
