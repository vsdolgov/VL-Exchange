# Экспериментальный исполнитель асинхронных сценариев VLSP

`AsyncScenarioExecutor` исполняет один и тот же `Scenario.process` для кадров и ответов MLLM. `services.submit_mllm` лишь подготавливает задание; отдельный worker обращается к модели только после транзакционной фиксации состояния и outbox в одном SQLite. `process_completion` атомарно фиксирует состояние, event journal и отметку о доставке результата. Сценарий и provider должны быть доверенными; код не является песочницей.

Операционный путь: `AsyncScenarioExecutor.open_protected(..., verifier=..., host=..., async_models=..., store=..., installation_signing_key=..., snapshot_media=..., discard_media=...)`. Host задаёт привязку модели и проверку её прав, безопасный media snapshot и политику доступа. Перед каждым сетевым вызовом сохраняется подписанный, привязанный к job и attempt [экспериментальный снимок разрешения](../../../security-runtime/PERSISTENT-LEASE.ru.md); его проверяют перед вызовом и перед фиксацией ответа. Новый grant не делает действительным результат по истёкшему исходному grant. После restart требуется снова открыть защищённый пакет и привязать ту же лицензию к хранилищу.

`AsyncStore` также поддерживает отдельный низкоуровневый режим с тестовым `authorize` callback; он сам по себе не является защищённой поставкой. [demo.py](demo.py) демонстрирует именно этот режим с имитатором. Полный защищённый пример с внешним сервисом не включён в эту публичную выборку; для него необходим отдельно настроенный provider и доверенная среда.

## Аппаратная привязка асинхронной модели

Для сценария с обязательным `org.vlexchange.hardware-async-models.v1` в `open_protected` дополнительно передаются `hardware_adapter` и `hardware_authorities={alias: bound_authority}`. Адаптер должен проверять подписанный allowlist и идентичность overlay, устройства и артефактов; авторитет создаётся из открытой защищённой лицензии модели после успешного выбора. Host держит открытыми оба защищённых контекста, владеет доверенными ключами и обеспечивает неизменность артефактов и фактическое размещение. Идентификатор `model_digest` асинхронной модели обязан равняться точному digest базового манифеста VLMP. `null` или digest произвольного checkpoint не создают разрешённой аппаратной привязки. Старый исполнитель отклоняет неизвестное обязательное расширение.

Выбранный `hardware_manifest_sha256`, вариант, устройство и точные артефакты входят в identity задания и его `job_id`. Перед постановкой, dispatch, provider, завершением и доставкой подписанный выбор и лицензия перепроверяются. При dispatch исходный model lease подписывается на конкретные job/attempt и фиксируется отдельно от lease сценария. Для завершённого hardware-задания оба исходных lease дополнительно проверяются перед вызовом completion и непосредственно перед фиксацией состояния; их удаление, изменение, истечение или смена варианта приводят к отказу. Новый online grant не продлевает ранее подписанный lease. После restart host должен заново открыть те же лицензии и сформировать эквивалентные доверенные адаптер и authority. Это относится к новым hardware-bound jobs; прежняя wire-форма и поведение старых заданий сохраняются.

При одновременной синхронной модели передайте отдельный `sync_hardware` для её ролей; `hardware_adapter` остаётся для асинхронных ролей. Синхронный вызов и постановка async job фиксируются одной транзакцией: истечение исходной синхронной лицензии до commit откатывает состояние и очередь. Provider остаётся доверенным host-интерфейсом: запись идентичности не доказывает, что удалённый сервис действительно использовал указанные веса и устройство. Для этого нужна независимая аттестация или локальный контролируемый исполнитель.

В offline и online режимах проверены запрос к реальной модели на синтетическом кадре, обработка следующего кадра до доставки ответа, перезапуск, корреляция, атомарное применение и дедупликация. Online-issuer был локальным тестовым сервисом. Идентичность checkpoint сообщена работающей системой, криптографическая аттестация весов не проверена.

Ограничения: один узел SQLite, доверенные host/администратор/часы, отдельные права на МЛЛМ и данные. Prompt, ответы и metadata находятся в SQLite, снимки хранятся отдельно; необходимы защита, retention, квоты и очистка осиротевших снимков после аварии. Повтор внешнего запроса после crash возможен; `Idempotency-Key` посылается, но соблюдение провайдером не подтверждено. Event journal не предоставляет готового внешнего API доставки/ack. Нельзя запускать дополнительные services из completion callback; reset run с историей заданий запрещён. При переиздании лицензии нужна отдельная контролируемая миграция или повторная постановка jobs. JSON state/job/result ограничены 65 536 байтами; media — 10 МиБ. Дополнительно перед вызовом provider фактический размер image bytes и компактного UTF-8 payload вместе не может превышать `max_input_bytes` объявленной модели.
