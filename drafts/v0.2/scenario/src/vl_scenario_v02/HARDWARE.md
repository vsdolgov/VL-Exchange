# Опциональная аппаратная привязка в ScenarioExecutor

`HardwareAdapter` — прототип мостового слоя для доверенного host; он не меняет файлы существующего сценария. Аргумент `hardware=adapter` поддерживается в `ScenarioExecutor(..., policy='development')` и в `ScenarioExecutor.open_protected(...)`. Без аргумента поведение прежнее. Защита и проверка лицензии самого сценария всегда выполняются штатным verifier до подготовки аппаратного варианта. Development используется только для разработки.

Конструктор `HardwareAdapter` получает подписанный конверт политики, доверенные `trust_anchors`, `now()`, заявки `requests`, фактические `devices`, настоящий `select` из hardware-portability/scenario и `validate_package` из аппаратного VLMP. Он также получает доверенные callbacks `authorize_license`, `attest_compatibility`, необязательный `verify_quality`, `acquire_lease(role, selection)` и `model_factory(role, selection, artifact_bytes)`.

`model_factory` возвращает inference callback и обязана загрузить именно предоставленные неизменяемые байты артефактов, не делать незаявленного fallback и обеспечить надлежащее устройство. Ключи `artifact_bytes` — подписанные пути, значения — `bytes`; их SHA-256 сверен с подписанной привязкой. Граница доверия: сторонний Python callback может проигнорировать эти требования, и сам адаптер не доказывает фактическое размещение модели. Загрузка целой модели в память — ограничение прототипа для крупных моделей; production host должен заменить её безопасным неизменяемым snapshot и подтвердить те же гарантии.

`acquire_lease` обязана получать настоящий авторизационный lease модели, привязанный к подтверждённым роли, устройству, варианту и лицензии, у доверенной системы защиты. Lease предоставляет `assert_current()` и относится к конкретному вызову: адаптер проверяет его до и после inference, затем до фиксации состояния и события. Проверка нового grant не заменяет проверку исходного lease. Просто вернуть объект с методом, всегда выдающим успех, допустимо только в тестовом примере и не является лицензированием.

Селектор повторно вызывается при подготовке, перед inference, после inference и перед фиксацией результата. Он повторно проверяет подпись по доверенному ключу, срок политики, целостность overlay, совместимость и callbacks разрешений. Неоднозначность, изменение артефакта, лицензии или политики приводят к отказу. `adapter.prepare(manifest_bytes)` и `adapter.assert_current(manifest_bytes, role, selection)` предназначены также для доверенной интеграции очереди; они сами по себе не запускают inference.

Внешний контекст защищённого аппаратного пакета и его ключи должны оставаться действующими весь жизненный цикл исполнителя и очереди. Для связи с `HardwareLicense.before_inference()` host использует только entry и variant, полученные в процессе **успешного** выполнения реального selector и сверенные с точной выбранной identity. Вызов `authorize_license` во время поиска кандидатов сам по себе не означает, что selector успешно завершился: промежуточный callback нельзя использовать как разрешение на выполнение.

Тест `scenario-package-v0.2/tests/test_hardware_integration.py` выполняет существующий пример color-cascade через ScenarioExecutor с фактическими FP32/квантованными ONNX-графами и реальной Ed25519-подписью. Лицензия модели в этом тесте имитируется; полноценная защита проверяется отдельными интеграционными испытаниями. Устройство CPU, остальные компоненты детектора/трекера — тестовые; совместимость Box 5/NPU не заявляется.
