# VLSP v0.2 — дополнительный профиль асинхронных MLLM

**Статус: финальная редакция дополнительного профиля проекта VL Exchange.** Дополнительная capability `async-mllm-v1` расширяет [синхронный VLSP v0.2](SPECIFICATION.md). Документ устанавливает требования к реализации; его публикация не означает принятия отраслью или того, что каждый v0.2 host, реальная MLLM, отказоустойчивое промышленное хранилище или интеграция с текущим ScenarioExecutor уже проверены. Профиль не требует VLBP, редактора, NRI, конкретной БД, API-провайдера, сетевого протокола или внешней системы для управления задачами.

Ранее опубликованные идентификаторы схем `urn:vl-exchange:scenario-async-mllm:0.2.0-draft` и `urn:vl-exchange:scenario-async-sequence:0.2.0-draft` сохранены как постоянные идентификаторы для совместимости. Суффикс `-draft` в их буквальном значении не определяет статус этой редакции профиля; `draft/2020-12` в `$schema` обозначает версию метасхемы JSON Schema.

## 1. Задача, версии и объявление capability

Сценарий может запустить длительный анализ текста и/или изображения мультимодальной языковой моделью (MLLM), продолжить обработку следующих кадров и позже обработать отдельное сообщение о завершении анализа. Это **асинхронный контракт с заданиями**, а не Python-блок и не обещание параллельности любых вызовов `services.infer` sync core.

Пакет обязан включить `async-mllm-v1` в `required_capabilities` и объявить именованные MLLM dependencies в обязательном namespaced расширении `org.vlexchange.async-mllm.v1`. Для каждого alias описываются предназначение, идентификатор и зафиксированная версия модели или иной устойчивый идентификатор версии, ожидаемые виды входа/выхода, ограничения размера и необходимые права. Допускается локальная модель VLMP или внешняя модель: отсутствие возможности получить криптографический digest у внешнего провайдера должно быть явно отражено в отчёте, а не заменено неподтверждённым hash. Host обязан проверить совместимость объявления и выданных ему model bindings до импорта. Другая версия модели или prompt/schema без явного объявления не является эквивалентной по умолчанию.

v0.1 и v0.2 sync-only host, не понимающий required capability или extension, обязан отклонить пакет до Python import; он не может молча запустить сценарий без MLLM. Соответствие sync core не означает соответствия этому профилю. Конкретная реализация вправе включить только часть описанных ограничений, но должна явно сообщить об этом и не заявлять полное соответствие.

Этот профиль расширяет вход процесса: наряду с `inputs={"frame":...}` разрешено отдельное `inputs={"mllm_result":...}`. Процедура `Scenario.process(inputs, context, state, services)` получает один из вариантов, а не оба сразу. `input_contract` sync core по-прежнему объявляет основной frame ingress; дополнительный тип completion и его схему объявляет extension. В остальном сохраняются события и правила состояния core. Один только валидатор core для `golden` с frame-only schema не подтверждает соответствие async: для completion применяется [async-sequence.schema.json](schemas/async-sequence.schema.json) и нужен соответствующий host runner. Подмена MLLM-ответа JSON-классификацией не допускается.

## 1.1. Python ABI постановки

Во время вызова с `inputs={"frame": frame}` сценарий с согласованной capability может подготовить задание следующим вызовом:

```python
receipt = services.submit_mllm({
    "model_alias": "vision",
    "frame_id": frame["frame_id"],
    "frame_ref": frame["frame_ref"],  # или None для text-only
    "bbox": None,                    # либо normalized xyxy внутри текущего объекта
    "tracker_alias": "tracker",     # из track текущего кадра, либо оба поля None
    "track_id": "track-7",
    "payload": {"text": "Опиши объект", "response_schema": {"type": "object"}, "parameters": {}},
    "deadline_ms": 1700000050000,    # пример; при запуске задаётся будущий UTC deadline
})
# receipt == {"job_id": "<64 lowercase hex>", "status": "staged"}
```

Набор полей request и receipt точный. `frame_id` должен совпадать с текущим входом, а ненулевой `frame_ref` — с временной ссылкой этого входа. Если указан `bbox`, host проверяет его по текущему объекту и сохраняет в защищённом snapshot правильный crop; при `frame_ref` и `bbox=None` сохраняется полный кадр. Оба поля `bbox` и `frame_ref` равны None для text-only. Track и tracker задаются парой и должны принадлежать текущему source/run и результату track для текущего кадра. Host выводит tenant, installation, scenario identity, source/run, исходное время и model revision из доверенной конфигурации и контекста; сценарий не может их подменить. `payload` и model alias проверяются относительно capability и разрешений до постановки.

`status="staged"` означает только подготовку: до успешного atomic commit задания не видно worker и обращение к MLLM не выполняется. Сценарий может сохранить `job_id` в возвращаемом JSON state; `frame_ref` и секреты сохранять туда нельзя. Если host создаёт media snapshot до commit, он обязан удалить невостребованный snapshot после rollback. На completion host вызывает тот же `process` с `inputs={"mllm_result": completion}` по схеме раздела 3 и исходным namespace; для этого требуется отдельный async-capable host. Экспериментальный `AsyncScenarioExecutor` и SQLite store реализуют этот путь; sync-only `ScenarioExecutor` по-прежнему отклоняет async capability. Сквозная проверка ограничена конкретной моделью, host и синтетическим кадром; её частный технический журнал в этой публичной выборке не включён.

## 2. Логическая модель и корреляция

Есть три независимые сущности: наблюдение исходного кадра, задание MLLM и позже обработанное сообщение о результате. Задание фиксирует идентичность сценария и его версии, alias и версию модели, request/job ID, `source_id`, `run_id`, `frame_id`, опциональный `track_id`, исходное время кадра и ожидаемый формат ответа. Если track_id задан, его namespace включает как минимум source/run и tracker alias; совпадение ID между камерами или перезапусками само по себе не связывает физические объекты.

Host гарантирует неизменность связки идентичностей на протяжении жизненного цикла job. Namespace содержит как минимум tenant/установку, scenario_id и версию и manifest digest сценария; при наличии track_id указывается и tracker alias. Эти значения выдаёт доверенный host, а не код загруженного сценария. Один и тот же request/job ID в таком namespace указывает на один неизменный запрос. Идентичный повтор submit обрабатывается идемпотентно, не создаёт новое логическое задание; повтор ID с другими входами/моделью/корреляцией отклоняется. Упорядоченная или доменно разделённая функция получения ID и канонизации входов должна быть документирована и проверяться тестовыми векторами конкретного профиля. Нельзя использовать текущий timestamp процесса как единственное основание identity или deduplication.

Ограничение экспериментальной реализации: `AsyncScenarioExecutor` отклоняет идентичное повторное `submit_mllm` в пределах одного вызова `process`. Поэтому её нельзя считать полностью соответствующей правилу идемпотентного повтора выше без устранения этого расхождения и повторной проверки; дедупликация на других границах не доказывает соответствия этому случаю.

[Векторы локального outbox prototype](async-reference-id-test-vectors.json) показывают детерминированное построение его ID по точным исходным байтам в вариантах с изображением и с одним текстом. Это **reference-specific** примеры Python JSON serialization, а не утверждённый межъязыковой стандарт каноникализации. Для совместимости между независимыми языками/host необходимо отдельно утвердить каноническое представление всех допустимых JSON-значений, включая числа и Unicode, и сверить реализации по общим векторам.

Исходные `frame_id` и `source_event_time_ms` в ответе — **корреляция**, а не время появления ответа. Host передаёт completion отдельным сообщением `mllm_result` тому же source/run с собственной последовательностью commit и собственным временем обработки; исходное время кадра хранится отдельно. Поэтому пришедший позже результат не использует повторно sequence исходного кадра и не нарушает требование sync core к порядку. Новый результат должен быть связан с исходной заявкой по полному набору identity и прав; ответы не сопоставляются по позиции массива или одному timestamp.

## 3. Вход, результат и граница данных

Логический `submit` задаёт хотя бы текст или изображение и разрешённую модельную роль. Текст — UTF-8 со scalar Unicode и явным верхним пределом. Изображение передаётся через host-controlled media reference, а не произвольный URL/path или секрет из пакета. В запросе могут быть schema структурированного результата, максимальные размеры, версия prompt/контракта, deadline и явно разрешённые параметры модели. Исходный frame_ref sync core действует только во время текущего вызова; для долгого job host должен создать собственный snapshot/handle с зафиксированными source/run/frame, digest и сроком действия и не должен выдавать frame_ref sync core за долговечный объект.

`max_input_bytes` объявленной роли модели ограничивает сумму **байтов компактной UTF-8 сериализации объекта `payload` и исходных байтов media snapshot**, фактически передаваемых adapter провайдеру; при text-only размер media равен нулю. Для измерения payload используются `sort_keys=true`, `ensure_ascii=false`, `allow_nan=false` и разделители `(',', ':')`; размер JSON-обёртки transport, base64 и прочего framing в это значение не входит и может дополнительно ограничиваться host. Сначала host проверяет доступный ему размер payload, а после разрешения media reference и проверки digest/срока повторно проверяет сумму **до вызова provider**. Превышение приводит к явной ошибке и не отправляет запрос. Приватная ссылка на media или метаданные сами по себе не заменяют проверку размера содержимого.

Host проверяет право сценария и получателя модели на работу с изображением/текстом и выдаёт worker минимально нужный доступ. Куда данные покидают площадку, разрешённые endpoint, учётные данные и политику retention настраивает доверенный администратор host отдельно от поставки; пакет не управляет учётными данными, не переносит их и не может подменять endpoint. Для удалённого соединения host обеспечивает аутентификацию сервиса, конфиденциальность и проверку подлинности канала в соответствии с политикой эксплуатации. Онлайн-обращение к MLLM может использоваться и при offline-лицензии сценария, если доступ к модели и политика данных разрешают это; offline-режим лицензии не означает, что MLLM работает без сети.

Успешный ответ несёт статус, request/job ID и всю корреляцию, точную объявленную модельную роль/версию и результат: текст, структурированные данные или оба. Structured данные проверяются по объявленной self-contained JSON Schema до применения, с ограничениями размера и глубины; unsupported fields, невалидный JSON, nonfinite числа и некорректный Unicode отклоняются. Ответ модели считается непроверенными данными, а не инструкциями для host или источником прав. Text-only input/output допустим, если разрешён конкретной модельной ролью. Ошибка, timeout, отказ или отмена задаются отдельным конечным статусом и не превращаются в пустой успешный результат.

Машинные формы extension, job и completion — в [async-mllm.schema.json](schemas/async-mllm.schema.json); [синтетический fixture](async-message-fixture.json) показывает корректные формы и ошибку `failed` без error, но его job_id — placeholder, не тест вычисления hash. Экспериментальный outbox экспортирует совместимые формы wire job/completion; полный перечень требований профиля ещё не сертифицирован в независимых host. Schema определяет форму, но не заменяет проверку корреляции, истинности модели, сроков и прав. Все поля времени с суффиксом `_ms` — UTC Unix milliseconds; adapter обязан явно преобразовывать другие единицы.

## 4. Атомарность запуска и получения результата

В ходе обработки кадра сценарий **подготавливает** задание, а host валидирует разрешения и входы. До успешного commit сценарного состояния задание не должно становиться видимым worker и не должно запускать внешнюю MLLM. Host атомарно фиксирует сценарное состояние/порядок и задание в устойчивом outbox либо применяет механизм с эквивалентной транзакционной гарантией. Ошибка лицензии, истечение исходного execution lease или сбой валидации до commit означает отсутствие нового job и отсутствие фиксации состояния. Задание отправляется провайдеру только после подтверждённого commit.

Worker обрабатывает job вне тракта приёма кадров. Полученный ответ проверяется на целостность и соответствие request/job identity, модели, source/run/frame/track и формату. Применение результата сценарием и отметка о его доставке/потреблении фиксируются атомарно вместе с новым состоянием в одной области транзакционности. Конфликт версии состояния приводит к явному повтору на актуальной версии или ошибке, но не к потере обновления. До фиксации результата снова проверяются действующие права сценария и модели; новый lease не делает задним числом действительным вызов, начатый с истёкшим lease. Нельзя считать две независимые базы или память процесса атомарно согласованными без подтверждённого механизма между ними.

Локальная идемпотентность не обещает **exactly-once сетевой вызов MLLM**. При аварии после отправки и до сохранения ответа worker может выполнить запрос повторно; remote provider может не поддерживать идемпотентность. Host передаёт стабильный idempotency key, если протокол провайдера это поддерживает, документирует политику ограниченного повторения, возможные дубликаты и стоимость. Повторная доставка идентичного terminal result не должна второй раз менять state или порождать событие; конфликтующий результат с тем же ID отклоняется и аудируется.

## 5. Жизненный цикл, out-of-order и восстановление

Модель состояний host как минимум различает принятое/ожидающее задание, исполняемое, успешно завершённое, отказ, timeout и отмену. Переходы, включая worker lease и его истечение, должны быть определены и атомарны; terminal status нельзя молча переписать другим. Время deadline — доверенное wall-clock время host; оно не выводится из event_time кадра. Timeout должен фиксироваться даже если provider не ответил. Если до завершения операции истекли лицензия на сценарий/модель или разрешение на данные, host блокирует применение; своевременное продление и политика отказа описываются отдельно.

Несколько jobs, даже на один источник/трек, могут завершиться в любом порядке. Сценарий обязан явно выбрать и документировать, использует ли каждый успешно коррелированный ответ, только ответ последнего запроса или другую versioned policy. По умолчанию результат, доставленный после terminal timeout/cancel, не применяется и фиксируется в аудите; реактивация/коррекция требует отдельной объявленной политики. Reuse track_id после пропуска и окончание жизни трека не должны превращать старый ответ в оценку нового объекта: используются исходные identity и namespace, а применимость результата проверяется сценарием по сохранённому состоянию.

Запрос на cancel фиксируется устойчиво. Успешная локальная отмена блокирует последующее применение результата, но не гарантирует физическую остановку исполнения на внешнем провайдере; нельзя утверждать удаление уже переданных данных без подтверждения провайдера. После restart host восстанавливает задания и состояние из persistent storage, учитывает истёкшие worker leases/deadlines и продолжает согласно политике; процесс с in-memory job queue не соответствует требованию restart persistence. Медиа должны оставаться доступны согласно ограниченному retention либо приводить к явной ошибке `media_unavailable`, а не к анализу другого кадра.

## 6. Security и проверяемые границы

Экспериментальная реализация устойчивого снимка исходного разрешения для job/attempt описана отдельно: [persistent lease](../../security-runtime/PERSISTENT-LEASE.ru.md). Это вариант reference host, а не обязательный межъязыковой формат профиля.

Применяется [общий security profile](../../../../docs/security/SPECIFICATION.ru.md), отдельно для сценарной поставки и прав MLLM/моделей. Даже при доверенных администраторе и издателе host обязан ограничивать данные и сетевые права, проверять model response как недоверенные данные и не допускать произвольное выполнение текста ответа. Защита закрытого scenario ZIP не шифрует автоматически отдельно хранящиеся медиа, журналы, prompt или веса модели; конфиденциальность и удаление данных требуют эксплуатационных механизмов.

Тестирование настоящего MLLM не следует из выполнения локального тестового provider adapter. Полное подтверждение профиля требует проверяемых версий и тестовых векторов, реального сценарного пакета и двух host, persistent restart/конкуренции и crash windows, изоляции media/identity и отказов прав, а также отдельного теста реального поставщика модели. Истечение grant и отказ модели в ходе запущенной операции не гарантируют прерывания уже отправленного запроса: запрещено принятие результата и последующий commit без действующих прав.

## 7. Conformance

1. Capability и extension объявлены; host без async support отказывает до import; sync-only/v0.1 не считает capability выполненной.
2. Несколько заявок с различными source/run/frame/track/model и временем применяются строго к своим состояниям; out-of-order completions проверяют документированную политику, а не привязку по порядку ответов.
3. Проверены идентичный повтор и конфликт ID/payload, два worker с конкурирующим claim и устаревший lease/token, дублирующий/изменённый completion, атомарность state + enqueue и state + result-consumed, rollback до обоих commit.
4. Пройден restart процесса с заданиями в очереди и в работе, recovery истёкшего lease, timeout, отмена, late result и отсутствие media. Подтверждение применимо к фактически проверенному persistent backend, не к любой БД.
5. По сериализованным test vectors проверяются identity и точные `request_id/source_id/run_id/frame_id/track_id` и модельная версия, формы text/image input, structured output schema и error/timeout responses.
6. Offline/online лицензии сценария, отдельные права на MLLM, политика egress и доступ к media проверены отдельно. Тестовый provider не выдаётся за реальную модель, локальный adapter — за стороннюю платформу, а именно SQLite — за нормативную зависимость.
