# VLSP v0.2 — проверка соответствия

Этот список — требования, а не отчёт о прохождении. Для каждого пункта фиксируются PASS, FAIL или NOT TESTED с версиями, хешами и наблюдаемой средой.

1. v0.1 и v0.2 различаются по version/contract; неподдерживаемый профиль отклонён до импорта. Unknown required capability, undeclared file/symlink, altered hash и неверная модельная ссылка приводят к отказу.
2. Manifest объявляет aliases конкретных VLMP-версий/профилей и реализации tracker. По каждой роли отдельно отражены наличие, фактический вызов, права, backend и результат; одинаковые aliases запрещены, одинаковые digest не выдаются за разные модели.
3. Один кадр передаётся через scoped frame_ref; чужой, подменённый или использованный после закрытия вызова ref отклонён. Проверяются размеры, source/run/frame identity, UTC timestamp и порядок sequence; состояние источников независимо.
4. Проверяются два detector aliases, возвращающие одинаковый raw object_id: wrapper даёт разные frame-scoped IDs по нормативному алгоритму. Тот же объект классифицируется для разных моделей с сохранением object_id/frame/alias; подмена ID, bbox, превышение границ и непринадлежащая detection отклоняются.
5. Реальная заявленная модель детекции, трекер и как минимум два реальных классификационных вызова дают результаты для двух объектов на нескольких кадрах. По каждому вызову записано inference_executed и достоверная идентичность модели; настоящие модели с разными manifest digest требуются для заявления о нескольких **разных** моделях. Synthetic модели отдельно маркируются.
6. Tracker-state передаётся и возвращается явно, не мутирует входные значения, независим по source/run, сбрасывается по контракту. Golden-тесты сценария проверяют корректную привязку состояния к каждому tracker alias: произвольный JSON сам по себе не гарантирует эту привязку на уровне host. Проверены запрет дублирующихся track_id и неизвестного object_id, обрыв track, новый объект и replay/reset согласно версии трекера.
7. Проверены неизвестный alias, недоступная/неверная модель, некорректные input/output, исключение сервиса, ошибка сценария, limits/calls/deadline, невалидная лицензия до import и expiry при выполнении: нет commit state/order/events и нет silent fallback. Результаты содержат конкретные стадии и политику recoverability; отсутствие events не маскирует исключение.
8. Тот же неизменённый ZIP запущен двумя независимыми host, результаты сопоставлены согласно версиям/допускам. Security: offline и online отдельно, один и тот же plaintext package digest, реальные подписи/encryption и заранее доверенные ключи; online loopback server не является production deployment.
9. Есть отдельный отчёт о том, какие компоненты реально выполнены, а какие смоделированы; hard preemption, платформа конкурента, GPU, cross-camera и async/late results отмечены NOT TESTED при отсутствии проверки. Дополнительно для регрессии запускаются неизменённые v0.1 тесты.
10. Все применимые векторы [error-vectors.json](error-vectors.json) выполняются двумя host без отображения code/stage через таблицу синонимов. Сравниваются исходные `stage`, `code`, `fatal`, `retryable`; message может различаться. Для каждого process failure проверяется отсутствие commit state/order/seen/events и соответствующий следующий вызов/reset/close. Для неуспешного preflight сценарий не импортируется, instance не создаётся.
11. Проверяются missing model и model digest/profile mismatch раздельно; испорченный ответ сервиса, исключение backend, изменение входа и timeout; service fault, перехваченный, изменённый или повторно выброшенный Python-кодом, остаётся fatal; закрытый/failed экземпляр и повторный close; истечение исходного lease после вычислений, повтор с прежним sequence после восстановления прав и отсутствие подмены lease при renewal. Никакая проверка core не заявляет hardware/GPU или async без отдельных векторов.
12. Дополнительные профили из [OPTIONAL-PROFILES.md](OPTIONAL-PROFILES.md) тестируются и заявляются каждый отдельно. Валидация JSON schema сама по себе не подтверждает preflight semantics, diagnostics без побочных эффектов, overload behavior или performance. Для capability report проверить exact contract/capability/profile, model/tracker binding и semantic attributes, unknown и null; для diagnostics — outcome/error и метрики/null/корреляцию; для streaming — реальную перегрузку и каждую заявленную политику. Неиспытанные части маркируются NOT TESTED.

Тестовый стенд МОЖЕТ связывать `frame_ref` с включёнными в inventory файлами изображений через отдельный каталог fixture, указывая source/run/frame, относительный безопасный путь и digest. Это соглашение стенда и способ воспроизвести golden input; оно не делает `frame_ref` путём в production и не заменяет проверку происхождения изображения принимающей системой.
