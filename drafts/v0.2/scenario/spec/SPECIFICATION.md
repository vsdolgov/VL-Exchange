# VL Exchange — VL Scenario Package (VLSP) v0.2

**Версия контракта: 0.2.0. Статус: проект для испытаний, не утверждённый отраслевой стандарт.** Термины ДОЛЖЕН/MUST, НЕ ДОЛЖЕН/MUST NOT, МОЖЕТ/MAY обозначают нормативное требование, запрет, возможность. Требование этой спецификации не свидетельствует о реализации или проверке в конкретном продукте.

## 1. Назначение и границы

VLSP — открытый межвендорный интерфейс исполнения Python-сценария в системе заказчика. Эксплуатационный код сценария поставляется закрытым лицензируемым пакетом. Сценарий может последовательно вызывать **несколько заявленных нейросетевых моделей и трекеров**, сопоставлять их результаты, хранить состояние и формировать события. Пример каскада: кадр → детектор → трекер → два классификатора → условие → событие. Вызовы выполняются принимающей системой через host services, а их последовательность задаёт Python-код сценария. Платформа-получатель не обязана иметь VLBP, NRI, Node-RED, граф, визуальный редактор или SDK VizorLabs.

Этот первый многомодельный профиль `python-scenario-services-json-v1` специфицирует **один текущий кадр на вызов**, синхронные результаты, прямоугольные normalized bbox, детекцию и классификацию, и трекер с явным JSON-состоянием. Несколько models/trackers, последовательные и условные вызовы и несколько детекций допускаются, но обязательного параллелизма нет. Обработка в нескольких источниках означает независимые namespace состояния; распределённое исполнение не предполагается.

Асинхронная доставка результатов MLLM определяется дополнительным [профилем async-mllm-v1](ASYNC-MLLM-PROFILE.md) и не входит в обязательный sync core. Смешение нескольких кадров в одном вызове, аудио, сегментация, 3D, потоковые тензоры, GPU и batching требуют отдельных профилей. **Вариант, когда host передаёт заранее рассчитанный набор наблюдений**, полезен, но не является частью sync core: адаптер не ДОЛЖЕН заявлять его реализованным без отдельной спецификации и проверок. По той же причине нельзя выдавать требование совместимости профиля за поддержку произвольных Python-библиотек, моделей или алгоритмов tracking.

Совместимость обеспечивается выбором версионированного профиля: v0.1 `python-scenario-json-v1` остаётся прежним, а v0.2 выбирается явным `spec_version` и contract. Реализация, поддерживающая только v0.1, отказывает v0.2 до импорта, а не интерпретирует его вход как classification. v0.2 host может поддерживать v0.1 через отдельный исполнитель; авто-конвертация или поддержка обеих версий не подразумевается.

## 2. Пакет, зависимости и identity

Пакет содержит `scenario-package.json`, `code/__init__.py`, `code/scenario.py`, другие заявленные файлы и golden sequences. Manifest — strict UTF-8 JSON по [scenario-package.schema.json](scenario-package.schema.json): в версии `0.2.0`, `format=vl.scenario-package`, `entrypoint.contract=python-scenario-services-json-v1`. Понятия `files`, `runtime`, `parameters`, `state`, `ordering`, `event_contract`, `golden`, `delivery` и `extensions` сохраняют семантику [VLSP v0.1](../../../../scenario/spec/SPECIFICATION.md); применяются те же ограничения чистого JSON, отсутствия неучтённых файлов/symlinks, полной инвентаризации, self-contained schemas, fail-closed на неизвестные required capabilities и контроля hash до импорта. Издатель не переиспользует пару scenario_id/version для другого содержимого. Каждый файл из `files` идентифицируется SHA-256, а manifest — hash точных байтов.

В v0.2 вместо `model_links` используется массив `models`: каждая запись содержит `alias`, `kind` (`detection` или `classification`), точный `manifest_sha256`, `profile` и `required`. Уникальный alias связывает логическую роль сценария с конкретным пакетом VLMP/профилем; две роли могут указывать на один digest, но это не подтверждает запуск разных моделей. `trackers` содержит `alias`, точные `implementation`, `version` и `required`; одинаковый alias недопустим в пределах своей категории. Трекер может быть алгоритмом, а не нейросетевой моделью. Перед импортом кода host проверяет наличие обязательных зависимостей, их заявленные идентичность, профиль и возможность исполнения; проверка хеша без вызова inference не является доказательством инференса.

В семействе существует ранее подготовленный VLMP `0.2.0-draft.1` для классификации с другим manifest/ABI; локальный детекционный draft не является его финальной редакцией и не может определяться только коротким номером `0.2`. Manifest сценария фиксирует kind, профиль и digest manifest модели; принимающий host проверяет конкретные format и версию по manifest с этим digest и фиксирует использованный адаптер в конфигурации и отчёте. Для этих сведений дополнительные поля в `models` сценарного manifest не вводятся. Совпадение номера не подтверждает совместимость схем или Box 5. Публикация общего model profile требует отдельного согласования.

Необязательная недоступная зависимость ДОЛЖНА быть явно представлена как недоступная. В этом профиле любой вызов недоступной зависимости и любая ошибка service делает весь process неуспешным, даже если Python-код перехватил исключение; silent fallback запрещён. Обнаружение доступности и продолжение после сервисной ошибки требуют отдельного профиля. Внешние модели/трекеры и их веса не содержатся в VLSP автоматически; их разрешения и защищённая выдача проверяются независимо. Один сценарный entitlement не создаёт право на любые внешние модели или трекеры.

Host фиксирует фактические версии Python, backend, модели, профиля, трекера, лицензий и hardware в отчёте; runtime без заявленной capability отказывает до импорта. Модели разных версий, фреймворков и весов не взаимозаменяемы только по alias или одинаковому формату ответа. Semantic description сценария ДОЛЖНО определять, что означает каждый event и от каких ролей моделей он зависит.

## 3. Вход и Python ABI

```python
class Scenario:
    def __init__(self, **parameters): ...
    def process(self, inputs: dict, context: dict, state: dict, services) -> dict: ...
    # close(self) необязателен
```

Вход — ровно `inputs={"frame":{"frame_id":str,"frame_ref":str,"width":int,"height":int}}`; descriptor frame_ref — opaque указатель host, не содержимое кадра, не путь и не внешний URL. Host adapter отвечает за фактическую привязку ref к кадру/source/run и его доступность только на время текущего process; wrapper проверяет соответствие frame_id/ref текущему входу. Нельзя сериализовать его для использования в другом вызове, выводить в events или считать передаваемым между host. Пример reference-моделей использует BGR uint8 HWC; фактическая модель и адаптер обязаны согласовать цвет, размер, crop, preprocessing и profile, а другая pixel convention требует явной совместимости. `width` и `height` — размеры исходного кадра в pixels, положительные integers. Статические формы: [services.schema.json](schemas/services.schema.json); проверки идентичности, времени, связности и порядка координат выполняются отдельно, поскольку форма JSON не выражает их полностью.

Context содержит только `source_id`, `run_id`, строго возрастающий `sequence` и неубывающий `event_time_ms` (UTC Unix ms) на пару source/run. `frame_id` уникален в рамках логического source/run и относится к конкретному кадру; повтор запрещён, если он не является явно управляемым replay после reset. Другим источникам разрешён независимый порядок; frame IDs и track IDs не предполагаются глобальными. Преобразование PTS в UTC — ответственность host. Кадры не сопровождаются автоматически сохранением или предоставлением их адресов сценариям из других вызовов.

Host передаёт только валидированные параметры в constructor, deep copies `inputs/context/state` и scoped service object. Возврат `process` — строго `{"events":[{"event_type":str,"payload":object}],"state":object}`; event candidates проверяются, ID, source/run, sequence и время назначает host по алгоритму `sha256-scenario-run-v1` из v0.1. Пустой events нормален. Изменять inputs/context нельзя; всё влияющее на последующее поведение состояние явно возвращается через state. Состояния источников/запусков изолированы. Нельзя подменять track_id, model alias, frame identity или время события позициями в массиве.

## 4. Model service

В ходе вызова сценарий может вызвать `services.infer(alias, request)` несколько раз, в том числе последовательно на вырезанных областях. `alias` обязателен в manifest.models и должен соответствовать `kind`. Request содержит ровно `frame_id`, `frame_ref`, `object_id` и `bbox`: для detection `object_id` и `bbox` равны null, для classification оба заданы. Classification crop относится к одному зарегистрированному объекту текущего кадра и лежит внутри bbox этого объекта; это может быть и весь bbox, и его подобласть. Координаты bbox — **исходного полного кадра** `[x1,y1,x2,y2]`, normalized на его width/height, конечные numbers в [0,1], `x1<x2`, `y1<y2`, координаты идут слева направо/сверху вниз. Правила округления/клипа crop и color/preprocess должны быть определены конкретным совместимым model profile и host; они не выводятся из самого bbox.

Detection response содержит `model_alias`, `frame_id`, `object_id=null`, `kind=detection` и `detections[]`. Каждый элемент имеет `object_id`, `label`, `category_id`, `score` и bbox; score конечен и входит в [0,1]. Classification response содержит те же корреляционные поля с `kind=classification` и `classification={label,score,category_id,output_index}`. Alias и frame_id ответа обязаны совпадать с запросом, object_id ответа classifier — с его crop. Отсутствие данных — пустой массив detection, но не ненужная подмена другой модели.

Raw detector object_id уникален только внутри одного ответа конкретного alias. Для исключения коллизий между моделями host wrapper присваивает выдаваемый сценарию object_id по алгоритму `sha256:` + SHA-256 следующих bytes: ASCII `VLSP-OBJECT-V1` и 00, затем для каждой из строк `model_alias`, `raw_object_id` — uint32 big-endian длина UTF-8 и её bytes. Строки — Unicode scalar values, кодирование UTF-8 strict без нормализации. Контрольные векторы с одинаковыми raw IDs у разных моделей и Unicode: [object-id-test-vectors.json](object-id-test-vectors.json). Эта идентичность относится только к `(source_id,run_id,frame_id)` и не является track_id; одинаковый object_id между кадрами не означает один физический объект. Host ДОЛЖЕН отвергать duplicate raw IDs в ответе модели и проверять в пределах вызова связность classifier/tracker результатов с выданными detections и исходным frame. Повторный вызов одного detection alias в том же process может вернуть тот же raw ID только для идентичной detection целиком; конфликтное значение приводит к ошибке. Hash обеспечивает namespace, а не гарантирует физическую идентификацию объекта. При коллизии hash host отказывает.

Host adapter отвечает за фактическое исполнение согласованной модели, преобразования входа и перенос точных output semantics. При ошибке inference, недоступности model/backend, выходе за deadline, некорректном идентификаторе, dtype или размере host выдаёт явную ошибку: пустой detection НЕ подставляется вместо ошибки. Сервисная ошибка делает текущий process неуспешным без commit, даже если исключение было перехвачено; recoverable service errors не входят в этот профиль. Потребность отслеживать provenance конкретной модели требует сохранять alias вместе с результатом, а не выводить его из label.

## 5. Tracking и сложная логика

`services.track(alias, request, tracker_state)` принимает `request={"frame_id":str,"detections":[...]}` с frame-scoped detection IDs и возвращает `{"tracker_alias":str,"frame_id":str,"tracks":[{"object_id":str,"track_id":str,"bbox":[...]}],"state":object}`. `alias` зарегистрирован в manifest.trackers. Каждая track observation ссылается на detection данного кадра и содержит её object_id; track_id определяется трекером и scoped как минимум `(scenario instance, source_id, run_id, tracker_alias)`. Один object_id в одном ответе tracker не назначается разным трекам, и один track_id не назначается разным объектам одного кадра.

В этом профиле tracker_state — явный конечный JSON без внешней persistence или скрытого состояния, влияющего на результаты. Сервис возвращает candidate next state, а сценарий включает его в возвращаемый scenario state; host фиксирует state только при успешном commit. Сценарий ДОЛЖЕН хранить и передавать каждому alias его собственное состояние; формат произвольного JSON сам по себе не доказывает, какому alias он принадлежит, и типовая проверка host не обнаруживает всякую подмену tracker_state. Отделение состояний разных source/run обеспечивает host, а правильную привязку состояния alias проверяют автор и golden-тесты сценария. Исходные state/detections не мутируются. Два вызова tracker по тем же входам и состоянию с той же реализацией/версией обязаны давать тот же результат по заявленной семантике/допускам. Порядок, привязка, потеря/восстановление, TTL, id reuse и поведение при пропуске кадров определяются **конкретной реализацией** и её конфигурацией; один и тот же ID из другого source/run не связывается автоматически. Неописанная совместимость состояний разных версий трекера не предполагается.

Сложная логика реализуется Python-кодом: ветвления, несколько последовательных model calls, сопоставления, временные условия по сохранённому состоянию, несколько событий. Она не зависит от внутреннего представления блоками. Код и объявленные зависимости входят в inventory; он не делает необратимых внешних бизнес-действий в ходе process и не исполняет скрытые сетевые callbacks. Передача frame_ref, объектов или секретов в events запрещена. Возможности работы с реальным временем, cross-camera association и асинхронные callback требуют отдельного контракта.

## 6. Atomic commit, порядок, ошибки, ресурсы

Для одного экземпляра синхронный `process` сериализован; обработка очередного frame начинается только после предыдущего результата. Дополнительная входная очередь может принять кадры до начала их обработки согласно [политике потока](OPTIONAL-PROFILES.md). Неупорядоченный sequence или убывающее UTC время отклоняется без model/tracker call и без фиксации. Асинхронные результаты MLLM обрабатываются отдельным согласованным [async профилем](ASYNC-MLLM-PROFILE.md), а не подменой sync input; этот core не задаёт watermark, late corrections или exactly-once сеть.

Host валидирует весь результат, candidate tracker state, максимальное число model/tracker calls, размеры, deadline и исходный ExecutionLease и только затем атомарно заменяет scenario state/ordering и возвращает события. Ошибка сервиса, некорректный ответ, неперехваченное исключение сценария или истечение исходного lease не приводят к фиксации state/order/events. Перехват сервисной ошибки сценарием не разрешает commit. Вызовы inference вычислительные и tracker функции чистые: они не гарантируют откат уже потраченных CPU/GPU ресурсов или побочных эффектов внешней системы. Сценарий не должен полагаться на внешние эффекты до commit; доставка событий потребителю и durable outbox не включены.

Любая ошибка сервиса делает вызов неуспешным, даже если код сценария её перехватил. Нормативные stage/code/fatal/retryable и переходы жизненного цикла sync-профиля определены в [ERRORS-LIFECYCLE.md](ERRORS-LIFECYCLE.md); этот документ уточняет наследуемые правила v0.1 и имеет приоритет для VLSP v0.2. Async-профиль сохраняет собственный контракт до отдельной проверки его реализации на эту таблицу.

`max_model_calls` и `max_tracker_calls` ограничивают количество сервисных вызовов на process; `max_process_ms` включает полное время синхронного ожидания services, но проверка после return не является hard preemption. Прочие byte/count limits наследуют v0.1 с уточнениями [ERRORS-LIFECYCLE.md](ERRORS-LIFECYCLE.md); этот же документ определяет правила ошибок и жизненного цикла v0.2. У принимающей системы могут быть дополнительные гарантированные ограничения на память, размер кадра, очереди и accelerator; их превышение — явный отказ, а не потеря входов без уведомления. Production host должен изолировать ресурсы/доступ к frame_ref и доверенным ключам.

## 7. Защита и лицензирование

Эксплуатация требует общий [VL Exchange Security](../../../../docs/security/SPECIFICATION.ru.md) profile `vl.exchange.protected` v0.1, поддерживающий подписанную offline-лицензию и online short-lived grant. Режим выбирается явно, trust anchors и ключи host задаёт доверенный администратор. License, manifest/archive digest, recipient и срок проверяются до доступа к сценарию и его import. Перед process захватывается `ExecutionLease`, тот же lease проверяется перед commit; renewal не продлевает задним числом начатый вызов. Требования защищённого запуска моделей/трекеров и их отдельные права определяются соответствующими пакетами/лицензиями.

Код издателя и администратор доверены, Python host не является sandbox. Полный клон защищённого окружения и ключей, компрометация процесса и администратор вне модели угроз; без соответствующих мер изоляции plaintext и кадры доступны доверенному исполнителю. Offline не предоставляет мгновенный удалённый отзыв. Безопасность зависит от приватности временной распаковки и невозможности подмены между hash-check и import.

## 8. Испытания и допустимые заявления

Применяется [CONFORMANCE.md](CONFORMANCE.md). Только декларация нескольких aliases, два вызова одного и того же ZIP или подставленные JSON fixtures не доказывают, что две разные модели действительно исполнялись. Демонстрация multi-model ДОЛЖНА сообщать фактические идентичности/профили, отличать настоящий inference от fixtures и не выдавать синтетические тестовые веса за промышленное качество детекции.

Версионированные дополнительные возможности описаны в [OPTIONAL-PROFILES.md](OPTIONAL-PROFILES.md). Реализация объявляет только фактически поддержанные профили; поддержка sync core не подразумевает их наличие. Они не меняют обязательные поля manifest и могут применяться к ранее сформированному пакету без изменения его байтов.

Для заявления о переносимости требуется **один и тот же неизменённый пакет сценария** в двух независимо написанных host, реальные заявленные модели и tracker, совпадение внешних событий/состояния по допустимым допускам, обработка нескольких объектов/источников и проверка ошибок/порядка/лицензий. Передатчик и получатель могут пользоваться общими формальными схемами и crypto-библиотекой, но две обёртки над одним executor не являются независимыми host. Полный контроль точности аналитики, GPU и система реального стороннего производителя — отдельные испытания и сами по себе не следуют из такого пилота.
