# VLSP 0.2 — дополнительные профили совместимости

Эти независимо согласуемые host-профили расширяют синхронный контракт, не меняют обязательный manifest, digest или код существующего ZIP. Профиль считается реализованным только если поддержаны его schema, семантика и испытания ниже; наличие документа не является доказательством реализации. Host, не поддерживающий profile, не ДОЛЖЕН заявлять его capability или интерпретировать требование профиля как поддержанное. Каждое объявление относится к конкретной установке/версии host и условиям эксплуатации. Конкретный формат доставки этих JSON документов и отдельный интерфейс регистрации схем согласуются сторонами; core не требует HTTP, брокера или визуального графа.

## 1. `vlsp.host-capabilities.v1`: предварительное описание host

При явном запросе host возвращает JSON по [host-capabilities.schema.json](schemas/host-capabilities.schema.json): `host_id`, поддерживаемые `contracts`, `capabilities`, `model_profiles`, `tracker_implementations`, `delivery_modes`, `data_semantics` и `limits`. `spec_version` и `contract` указываются совместно; сам профиль имеет формат `vlsp.host-capabilities` и версию `1.0.0`. Arrays могут быть пустыми. `limits.max_frame_width/height` — целые pixels или null, если проверенный предел неизвестен. Null не означает бесконечность и не доказывает возможность обработки конкретного кадра.

Для preflight проверяются точное совпадение пары spec/contract и наличие каждой требуемой package capability; kind/profile модели, tracker implementation/version и delivery mode должны присутствовать, если их требует пакет/развёртывание. Пересечение возможностей не выдаёт лицензии на модель и не заменяет проверку конкретного manifest digest, файлов, предоставленных binding и прав до import. Неизвестная required capability → `capability_missing`; отсутствующий обязательный binding → `dependency_missing`; несовместимый binding модели → `model_link_mismatch`. Ответ — декларация host, не гарантия существования устройства, качества, производительности, наличия лицензии или успешного запуска.

`data_semantics` задаёт registry entries `{semantic_id,version,attributes}` с устойчивыми идентификатором и версией и атрибутами-строками. При явно требуемом потребителем наборе атрибутов совместимы только одинаковые `semantic_id` и `version`, когда каждое требуемое имя имеет точно такое же значение у host; дополнительные атрибуты host допустимы. Неизвестный требуемый атрибут означает неподтверждённую совместимость, а не подстановку предположений. Этот механизм не допускает автоматически преобразовывать координаты или цветовое пространство.

Для основного frame/ref профиля нормативные значения: пространственная система coordinates `normalized-xyxy-full-frame` с началом сверху слева; `source_id/run_id/frame_id` задают область идентичности; timebase context — `unix-utc-ms`. Для конкретного model binding отдельно объявляются цвет, layout, dtype, resize/letterbox, crop clipping/округление и преобразование координат crop→full-frame. Пример одного entry: `{"semantic_id":"org.vlexchange.frame.xyxy","version":"1.0.0","attributes":{"coordinate_space":"normalized-xyxy-full-frame","origin":"top-left"}}`. Один только совпадающий JSON shape не подтверждает семантическую совместимость; значения являются характеристиками конкретного binding, а не безусловным свойством любого frame_ref.

Проверка: документ валиден по schema; неизвестная обязательная capability, отсутствующие semantics/attributes и неподдерживаемые profile/version обнаруживаются до исполнения; различаются неизвестный и отсутствующий предел; два разных model digest нельзя считать одной моделью. Негативный preflight не импортирует код сценария. Ошибки сравнителя именованных semantics в этом дополнительном описании должны явно сообщаться вызывающему, но отдельный код ошибки core не придумывается: применение приводит к соответствующему `capability_missing`/`model_link_mismatch`.

## 2. `vlsp.diagnostics.v1`: диагностическая запись

Для каждого наблюдаемого process host МОЖЕТ выпускать запись [diagnostic.schema.json](schemas/diagnostic.schema.json) формата `vlsp.diagnostic`, version `1.0.0`: `host_id`, digest сценария, source/run/sequence/frame, outcome, метрики, фактически вызванные model aliases/digests/counts и `error`. `outcome=committed` требует `error=null`; `failed/rejected` требует валидный [error.schema.json](schemas/error.schema.json). Source/run/frame относятся к принятому input; для некорректного или отсутствующего identity диагностическая запись этого вида не формируется. Это диагностика, не event и не доказательство успешной доставки.

`duration_ms` — монотонная длительность обработки, `queue_wait_ms` — ожидание перед приёмом в обработку; `queue_depth` — измеренная глубина очереди в момент приёма, `dropped_frames` — измеренное число кадров, отброшенных этим source/run с предыдущей записи. Неизмеренное поле = null, а не 0. Числа конечные и неотрицательные. `models.call_count` считает фактически начатые обращения на этот process; model alias/digest соответствуют установленному binding. Последовательная отсылка записи, её потеря или ошибка не должны приводить к повтору process, изменению state/events или потере атомарности; порядок записей, долговечность и exactly-once не обещаются. Сохранение/объём диагностики определяет host; запрещено включать frame_ref, кадры, ключи, токены и содержимое prompt.

Проверка: schema и outcome/error согласованы; показатели queue и обработки различимы, null сохраняется как неизвестное; идентичности, вызовы и ошибка соответствуют фактическому завершению. Инъекция ошибки diagnostics не меняет бизнес-результат. Измерение только FPS на выходе не подтверждает наличие очередных или покомпонентных метрик.

## 3. `vlsp.stream-policy.v1`: политика входной очереди

Дополнительная опция имеет формат `vlsp.stream-policy`, version `1.0.0`; описание по [stream-policy.schema.json](schemas/stream-policy.schema.json) привязано к одному source/run и задаёт конечную очередь `max_queue_frames`, `overload_policy` (`block`, `drop_oldest`, `drop_newest`), `max_wait_ms` и `on_end` (`drain`/`discard`). `block` замедляет подачу в границах host API; превышение `max_wait_ms` означает явный отказ входа. При drop политика прямо разрешает потерю входа, а host фиксирует пропуск в diagnostics/операционном отчёте; пакет/развёртывание, требующее каждый кадр, несовместимо с drop-политикой и `on_end=discard`. Для такого требования также нужна отдельная политика обработки отказа по timeout и потерь до очереди: один лишь `block` не гарантирует доставку и обработку всех кадров. Пропущенный до process кадр не меняет scenario state/order/seen/events. `on_end=drain` завершает принятые в очередь вызовы, `discard` явно фиксирует отброшенные кадры. Очередь ограничена; неявной подмены устаревшим результатом, другой моделью или тихой потери событий нет.

`max_queue_frames` и `max_wait_ms` задаются целыми JSON-числами без десятичной части или экспоненты; boolean и представления `1.0`/`1e0` не допускаются. Одна JSON Schema не гарантирует это ограничение: после структурной проверки требуется отдельная проверка числового представления. Предел очереди относится к ожидающим кадрам; выполняемый вызов в него не входит. Ограничение количества ожидающих кадров не является ограничением общей памяти процесса или числа одновременно заблокированных отправителей.

Структурированный отказ передаётся как нормативная ошибка исполнителя только при явной гарантии доверенного callback, что commit не состоялся; наличие у исключения метода сериализации само по себе такой гарантии не даёт. Необработанное исключение callback или потеря ответа транспорта могут произойти после commit: результат очереди в этом случае обязан явно обозначать `reason=callback_outcome_unknown`, `commit=unknown` и не должен представлять эту ситуацию как доказанный `scenario_exception` без commit. Это статус транспортной границы, а не новый код ошибки sync core; автоматический повтор и exactly-once не предполагаются. В локальных Python-адаптерах этой гарантии соответствует внутренний маркер доверенного callback `vlsp_no_commit=True`; он не является защитой от недоверенного кода.

Эта политика не вводит многокадровый process, parallel inference, fork/join, event-time windows, автоматические retries, hard preemption или exactly-once delivery. Порядок принятых в process кадров остаётся строго по sequence в каждом source/run; gaps допустимы. Источник, у которого нельзя реализовать block из-за устройства или протокола, ДОЛЖЕН явно отклонить такую конфигурацию, не менять её на drop. Порядок/лимиты и политику разрешённой потери указывают при развёртывании, а не выводят из имени модели.

Проверка: заполнить очередь быстрее, чем она освобождается, и проверить каждый заявленный overload mode, счёт пропусков и отсутствие state/events для неисполненного кадра; проверить stop/restart, отсутствие cross-source смешения, drain/discard и явно документированное поведение блокировки. Наличие однокадрового синхронного теста или измерение throughput не подтверждает этот профиль. Результаты каждой политики сообщаются отдельно.

## 4. Отчёт испытаний и оценка качества

Отчёт различает как минимум: schema и semantic conformance; одинаковое исполнение неизменного package у двух независимых host; аналитическое качество; эксплуатационные показатели. Для каждого раздела фиксируются PASS/FAIL/NOT TESTED, идентичность package/models, версия host, данные и окружение. Quality report указывает dataset/version/digest, разметку, taxonomy, thresholds, метрики и методы подсчёта. Performance report указывает аппаратную платформу, runtime/backend, конфигурацию, нагрузку и измеренные p50/p95/p99 latency, throughput, память и пропущенные кадры, если применимо. Непроверенный показатель маркируется NOT TESTED. Golden или совпадение выходов не доказывают accuracy, безопасность, внешнее внедрение или производительность. Стандарт не устанавливает единый проходной порог качества для всех сценариев.

Составной/декларативный граф, параллельный join и универсальная онтология объектов остаются отдельными будущими профилями: описанные возможности не требуют от стороннего host узлов VLBP, Node-RED или совпадающей внутренней реализации.
